# 安全中心代码架构

实现以本文件为准。产品背景见 [管家级安全中心架构.md](管家级安全中心架构.md)。两份不一致时，照本文件。

工程是 `apps/securitycenter`，包名 `com.jinyinhu.securitycenter`。现有 `probe/`、`report/`、`LiveStore` 保留。不改 P1 / P2 / P3 的 verdict 语义。

清理规则和重复文件算法自己写。不把 SD Maid SE 或 ClamAV 的源码译进本工程。SD Maid SE 是 GPL-3.0，ClamAV 是 GPL-2.0。Deep Cleaner 是 Apache-2.0，若摘录它的源码，保留其版权声明。

四个主功能要达到普通手机管家的厚度，而不只是有入口：

- 体检：一次跑完系统防护姿态、已装应用信誉、规则文件是否可读。圆环仍只有四句。可清理字节和敏感权限人数显示在首页，不决定圆环。权限异常进建议。P1 / P2 / P3 留在「系统防护自检」，体检不调用它们。
- 应用信誉：界面用这个名字。内部 `kind` 仍是 `malware`。已装应用，加上用户授权的文件。风险来自哈希黑名单、包名加证书黑名单、发行版登记证书不符、验签通过的云端风险。正常来自登记证书相符、文件白哈希、信任区，以及没有可疑命中时验签通过的云端正常。已装应用的权限组合只看已授予；安装包文件的权限组合看声明。权限组合和相似包名只产生可疑，不叫病毒。安装包能读出包名和证书时，走同一套判定。
- 垃圾清理：主列表是应用缓存和安装包。缓存默认勾选，确认后直接清除，不进隔离区，不删应用数据。安装包默认不勾选，确认后进隔离区。重复文件和大文件是清理页里的两项查找工具，本轮只列出，不隔离、不删除。
- 权限管理：敏感权限按组显示，能看到已授予还是已拒绝。系统允许时可以关闭一项授权，调用时带 `PERMISSION_USER_FIXED`。系统固定的权限不提供开关。最近使用只有接口可用时才出现。

做不到的系统接口仍显示「暂不支持」，不补假数据。软件管理、防护状态、记录和隔离区保留。本轮不实现态势服务进程。判定函数、端口和存储格式按第 10 节写，使以后的 `jyh_security_center` 可以原样接走，不必把判定再写一遍。

## 1. 依赖方向

只允许向下依赖。页面不读盘、不调包管理、不做哈希。功能模块互不 import。`task` 不 import `feature`。`engine/` 不 import 页面、任务、系统端口和网络。

```text
pages
  → task.enqueue / cancel
  → record.ResultStore.read
  → record.Disposition（仅用户确认之后，目标必须在当前已收口结果文件里）

task
  → RunnerRegistry（启动时注册，按 kind 查找）
  → 按 kind 组装第 3 节的窄上下文
  → record.Writer（唯一写盘执行者）

engine
  → Decide（纯函数）
  → AppJudge 只编排：本地步骤、收集 QueryKey、调用注入的 CloudBatch、再调用 Decide

端口实现
  record/     Writer、作业索引、结果文件、隔离区、信任区、审计
  system/     能力探测、包枚举、文件打开、卸载、缓存、授权、态势客户端
  cloud/      CloudBatch 的进程内实现
  probe/      现有探针。体检不调用

EntryAbility
  → LiveStore.prepare()
  → CenterStore.prepare()（含 Writer.recover）
  → SystemGate.probe()
  → RunnerRegistry.registerAll()
```

`JobRunner` 是进程内的组合根。它持有全部端口，但每个 Runner 的参数类型只包含自己的窄上下文。`ExamRunner` 的类型里没有清除、撤权、卸载和隔离。它有只读的 `files` 和 `open`，只用来调用 `InstallerScan.listInstallers` 统计安装包字节，不调用 `Quarantine`，也不 import `CorpseFinder`。`MalwareRunner` 和 `AppRunner` 的类型里没有缓存和撤权。两者有只读的 `GrantLookup`。`ExamRunner` 用已有的 `AccessFacts` 填同一组已授予权限，不另加端口。

体检、信誉页和软件页的应用结论用同一套 `Decide`。清理字节用 `CleanMath`，敏感权限分组用 `SensitiveCatalog`，安装包名单用 `InstallerScan`。这些函数放在 `engine/` 和 `center/`。体检在同一次 `ExamRunner.run` 里调用 `AppJudge`，把已判定的 `ScanHit` 写进这次体检的结果文件。不入队第二个 `malware` 作业，不打开信誉页，不调用 `probe/`。

卸载、隔离、信任、清缓存、关闭权限由页面调用 `Disposition`。`Disposition` 再把写盘提交给 `Writer`。`MalwareRunner` 不 import `AppRunner`。

结果说明 `note`：`ScanReport`、`CleanReport`、`FileToolReport` 重新打开时只显示这份字符串，禁止再根据 `complete` 重造「已达本次扫描上限」「结果较多，仅显示部分」或「目录未授权，未扫描」。多句用顿号连接，按下面的顺序，没有的句子不写。

- `ScanReport`：`已达本次扫描上限`、`结果较多，仅显示部分`、`目录未授权，未扫描`、`授权已失效`。
- `CleanReport`：`已达本次扫描上限`、`结果较多，仅显示部分`、`无法读取其他应用缓存`、`请先选择目录`。
- `FileToolReport`：`已达本次扫描上限`、`结果较多，仅显示部分`。

上限和截断只在 `complete===false` 时写入。授权目录和缓存身份这两类句子在 `complete===true` 时也可以有。`complete===false` 且 `note` 为空：页面显示「本次扫描未完成」，并打一条 hilog。这是写漏，不是另一种原因。

每一次 `query` 使用独立的 `nonce`。禁止进程内单槽 `nonce`。轻车道和重车道可以同时调用。取消只看本次传入的 `CancelFlag`，不得把另一次正在飞的请求标成整批 `offline`。

`CloudView.state !== 'reached'` 时，`level` 必须是 `none`。`Decide` 在 `state` 不是 `reached` 时忽略 `level`。手工构造 `state=offline` 且 `level=ok` 的值，结果也不得变成 `source=cloud` 的正常。

`toQueryKey` 只复制 `bundleName`、`versionCode`、`certSha256`、`sha256`。返回值上不存在 `id`、`version`、`label` 和 uri。

窄上下文在 `task/Contexts.ets`。`JobBase` 是公共的只读运行信息。写盘不在上下文里，Runner 把结果对象交给 `JobRunner`，由 `Writer` 落盘。

```ts
export interface FileToolContext {
  base: JobBase
  files: FileSource           // 只读
  open: FileOpen              // 只读
}
```

`duplicate` 和 `large-file` 只用 `FileToolContext`。这两个 Runner 没有缓存、包普查、卸载、撤权和隔离。安装包查找不是 `JobKind`。`CorpseFinder` 由 `CleanRunner` 在 `kind=clean` 里调用。禁止再增加 `corpse` 这个作业种类，也禁止为它入队。

`Disposition` 另持 `Quarantine`、`InstallerPort`、`CacheClear`、`AccessRevoke`、`TrustList`、`ResultStore`、`Writer`。页面不持有这些端口。

`ProbeMap` 只把已经产生的探针结果翻译成 `CheckItem`。它不运行探针。

## 5. 任务

`task/JobQueue.ets`

- 轻车道和重车道各有一个队列。同一车道同时只跑一个作业。轻车道不等待重车道。两条车道的计算可以重叠。
- 一切索引、结果文件、审计、隔离清单、信任区的写入都提交到 `Writer` 的同一条串行队列。车道结束时不直接改 `index.json`。
- `enqueue(request): string`。请求相同，指 `kind`、`scope`、`focus` 全等，且 `uris` 去掉空串、去重、按 UTF-8 字节序排序后逐项全等。相同请求已经 `queued` 或 `running` 时，返回已有 `jobId`，不新写一条。相同 `kind` 已经 `queued` 或 `running`、但请求不同时，返回空串，不入队，不改那条作业。页面显示「正在扫描」，并写明正在跑的是 `quick`、`full` 还是 `custom`，不要把正在跑的结果当成这次请求的结果，也不要用被拒绝请求的档去改进度句。`done`、`failed`、`cancelled`、`interrupted` 不占用这个名额。空串不是 `jobId`。成功入队的 `jobId` 非空，并且不得等于 `quick`、`full`、`custom`、`rules`、`sensitive` 或权限组名，也不得以 `anomaly:` 开头。路由参数要能靠这个区分作业和页面定位。
- 入队时立刻经 `Writer` 写 `JobRecord`，`state = queued`，`seq` 取当前索引里最大 `seq` 再加 1。索引为空或没有 `seq` 时从 1 开始。不使用 `Clock.nowIso()` 分配 `seq`。`startedAt` 用 `Clock` 只供记录页显示。随后转为 `running`。
- `Writer.recover()` 在 `CenterStore.prepare()` 里、任何 `enqueue` 之前运行。索引里残留的 `queued` 和 `running` 改为 `interrupted`，`finishedAt` 写 `Clock.nowIso()`，`seq` 保持入队时的值，`summary` 写「扫描已中断」。不补跑。`finishedAt` 不参与首页挑选。若该条是体检且结果文件能解析成 `ExamReport`，调用 `settleStoppedExam`。没有结果文件时不合成一份 `clear`。不改另一条已经 `done` 的体检。首页按第 14 节的 `homeExam()` 读取。`interrupted`、`failed` 或 `cancelled` 收口后若 `ExamReport.state` 为 `risk`，首页改读这份，不再留着上一份「暂无风险」。时钟回到错误年份时也一样：比较的是 `seq`，不是 `finishedAt`。
- `cancel(jobId)` 把该作业 `CancelFlag` 的共享整数设为 1。Runner 在每个对象之后检查。哈希 Worker 在每个分块之后检查同一块 `SharedArrayBuffer`。置上后停止后续对象，状态写 `cancelled`，`itemCount` 等于已处理数。若结果文件是 `ExamReport`，接着调用 `settleStoppedExam`。作业状态保持 `cancelled`，不改成 `interrupted`。
- `settleStoppedExam` 只改这份体检结果，不改其它 `done` 的体检，也不改作业状态。四个应用计数按等级取较大值：`summary` 里已经写下的数，以及这份 `apps[]` 里 `action===none` 的该等级行数。只在较大值高于 `summary` 时改写，并打一条 hilog。`summary` 里该等级已经更大时保持原数。禁止改写成截断后 `apps[]` 的行数，禁止把 `okApps` 或 `unknownApps` 改小。四个数都是 0、而 `apps[]` 里已有 `action===none` 的行时，用这些行数抬高对应计数。截断前已经写下的人数保持不变。`appsComplete` 已经是 true 的保持 true，禁止改成 false。它仍是 false 时保持 false：应用循环没写完、截断丢掉了 `unknown`，都留在 false。取消或进程退出发生在统计缓存、安装包的阶段，而应用循环已经写完时，详情不得出现「本次扫描未完成」。`anyOffline` 用第 8 节的定义。已有的 `exam.malware.apps` 若 `status` 不是 `unsupported`，用该项已写下的 `countsTowardState`、保持后的 `appsComplete`、改写后的 `riskApps` 与 `unknownApps`、以及 `anyOffline`，调用 `examAppsStatus`，替换该项的状态和详情，再按第 8 节补「云端暂无结果」和「部分应用暂无法确认」。`status` 为 `unsupported` 时不改这项，也不要把 `bundlesReady` 写成 true。可疑建议项用改写后的 `suspiciousApps`：大于 0 为 `attention`，否则 `ok`。该项不存在且 `suspiciousApps > 0` 时补一条，`id` 为 `exam.malware.suspicious`，`group` 为 `threat`，`kind` 为 `advice`，`countsTowardState` 为 false，动作与第 8 节相同。`suspiciousApps` 为 0 且该项不存在时不补。然后 `state = stateOf(items)`。应用信誉项还不存在时，不补一条通过项；`stateOf` 若得到 `clear`，改成 `incomplete`。`apps[]` 里有 `level=risk` 且 `action===none` 的行，或计入状态的项里已有 `risk` 时，`state` 必须是 `risk`。
- `report` 由 `JobQueue` 切回 UI 线程后，再写入 `AppStorage` 键 `center.job.light`、`center.job.heavy`。Worker 不写 `AppStorage`。首页订阅重车道。信誉作业的 `message` 含当前 `scope` 文案：快速、全盘或自定义。

`CancelFlag` 持有 4 字节的 `SharedArrayBuffer`，整数 0 表示继续，1 表示取消。传给 TaskPool 的是这块缓冲区，不是布尔值的副本。若本 SDK 的 TaskPool 不能共享这块缓冲区，哈希循环仍必须在每个分块之后读到同一份取消标志。禁止 UI 置取消后 Worker 把整个文件哈希完才停。验收第 9 款仍要满足。

作业已收口：`state` 为 `done`、`failed`、`cancelled` 或 `interrupted`。`queued` 和 `running` 不是。

`JobRunner` 只做组装和收尾。Runner 抛错时，作业记 `failed`，已写入的结果保留。若该条是体检且结果文件能解析成 `ExamReport`，调用 `settleStoppedExam`。没有结果文件时不合成一份 `clear`。作业状态保持 `failed`。`offline`、`unsupported` 是条目级结果，Runner 不得为它们把整次作业抛成 `failed`。

`RunnerRegistry.registerAll()` 在 `EntryAbility` 调用一次。注册表的键是 `JobKind`。

## 6. 判定

`engine/Decide.ets` 导出 `canonicalCert`、`terminalBeforeCloud` 和 `decide`。

```ts
export function canonicalCert(value: string): string

export function terminalBeforeCloud(
  fp: Fingerprint,
  rules: RulePack
): Verdict | null

export function decide(
  fp: Fingerprint,
  declared: string[],
  granted: string[],
  grantsReady: boolean,
  rules: RulePack,
  trust: TrustEntry[],
  cloud: CloudView
): Verdict
```

`canonicalCert` 按这个顺序做，这不是哈希。禁止对平台指纹再做一次 SHA-256。空串仍是空串。

1. 去掉首尾空白。记这一步的结果为原文，供第 5 步使用。
2. 去掉其中的空格、冒号和连字符。
3. 若结果以 `sha256`、`sha1` 或 `md5` 开头，不区分大小写，并且去掉该前缀后的长度分别是 64、40、32，剩余部分每个字符都是十六进制，则只保留剩余部分。纯 64 位摘要即使以 `sha256` 这几个十六进制字符开头，也不去掉，因为去掉后长度不是 64。
4. 若此时非空、长度为偶数、且每个字符都是十六进制，返回小写的这一段。
5. 否则返回第 1 步的原文，不再改大小写。

`SHA256:AA:BB…` 和 `SHA-256:AA:BB…` 因此与不带前缀的小写摘要相等。前缀加摘要不得再当作另一条证书指纹。

证书比较只用规范化之后的字符串，并且 `certAlgo` 必须相同。`Fingerprint.certSha256`、规则行和信任区里的证书指纹，写入前都先经过 `canonicalCert`。

`terminalBeforeCloud` 只做第 1 到第 3 步。命中则返回判决，`cloud=unchecked`。未命中返回 `null`。调用方不得把这个 `null` 显示成「无匹配规则」。它不返回第 6 步的 `ok`，也不返回第 8、9 步的 `unknown`。同一包名有多行时，顺序与下面 1 到 3 条相同：先看高置信黑规则，命中就返回 `risk`，不产生 `QueryKey`。没有黑规则、但有登记相符时，才返回 `null`，云批次照常跑，第 3 步的冒名不返回。没有相符、且构成冒名时，才返回冒名。禁止先看到登记相符就返回 `null`，从而把同时命中的黑规则送去云。

`decide` 按下面的表从第 1 步走到第 13 步。前一步结束就不再往下。直接调用 `decide` 时，第 1 到第 3 步仍然有效，避免云端 `ok` 盖过黑名单或冒名。`cloud.state` 只能是 `reached` 或 `offline`。传入 `unchecked` 时返回 `unknown`，`evidence=unchecked-cloud`，并打一条 hilog。这个返回值表示调用错误，不能当作扫描结论。`cloud.state` 不是 `reached` 时，忽略 `cloud.level`。第 1 到第 9 步不读取 `granted`。第 10 步才读。

`AppJudge` 先调用 `terminalBeforeCloud`。返回非 `null` 的对象不再产生 `QueryKey`。返回 `null` 的对象才进入云批次。白哈希、登记相符和信任都落在这个 `null` 里，都不能用来跳过云查询。批次有了 `reached` 或 `offline` 之后，每个对象只调用一次 `decide`。禁止先用 `unchecked` 调用 `decide` 再采用第 4 步以后的结果。`AppJudge` 不调用 `GrantLookup` 或 `AccessFacts`。调用方传入 `declared`、`granted` 和 `grantsReady`。

已装应用的 `grantsReady` 取 `SystemGate.grants()` 是否为 `ready`。为 `ready` 时，`granted` 是该包 `grant === 'granted'` 的权限名。`ExamRunner` 从 `AccessFacts.facts` 取。`MalwareRunner` 和 `AppRunner` 从 `GrantLookup` 取。`GrantLookup.ready()` 与 `SystemGate.grants()` 必须一致。`grantedOf` 的名字集合必须与 `facts()` 里该包已授予的权限名一致。文件对象的 `grantsReady` 固定为 false，`granted` 为空数组。

`AppJudge` 依赖 `CloudBatch` 接口。它不 import `ReputationClient`。`JobRunner` 把 `ReputationClient` 注进去。

| 13 | 以上都没有 | `unknown` / `local-rule`，在线时原因「暂无匹配结果」 | 禁止写成「未发现风险」「暂无风险」「无匹配规则」。离线时原因只留云失败的那一句，不写「暂无匹配结果」 |

第 4 步到第 13 步若 `cloud.state=offline`，`Verdict.cloud` 保持 `offline`。等级仍按上表里走得到的那一步。原因先写那一步的本地结论，末尾追加云失败的那一句。云失败的那一句按第 7 节三选一，全文都含「未联网」，本身不被截掉。第 4 步和第 11 步要求 `reached`，离线时走不到。第 13 步在离线、且没有本地结论时，原因只留云失败的那一句，不写「暂无匹配结果」，也不写「无匹配规则」。`cloud.state=reached` 且 `level=unknown` 时，第 6、7、12、13 步的原因末尾追加「云端暂无结果」。第 6、7 步的等级仍是 `ok`，`source` 不是 `cloud`。追加「云端查询正常」或「云端暂无结果」时，先截本地原因，再把这句放在末尾，总长不超过 `reasonMax`。这句本身不被截掉。「云端暂无结果」按第 8 节写入应用信誉项的 `detail`；该项为 `ok` 且圆环为 `clear` 时，圆环下方也写。「云端查询正常」只留在该行原因里，不写入应用信誉项 `detail`，也不写到圆环下方。信誉结果页的摘要只在第 9.1 节写「部分应用云端暂无结果」。

离线不把 `cloud.level` 当成 `ok`。第 5、6、7 步在离线时仍可以是 `ok`，此时 `source` 不是 `cloud`。禁止出现 `source=cloud` 且 `level=ok` 且 `cloud=offline`。禁止因为后来命中启发式而把 `cloud` 从 `offline` 改成别的值。禁止第 11 步把第 8、9 步的未知或第 10 步的可疑改成正常。禁止第 11 步把证书为空或 `certAlgo=none` 的包写成 `source=cloud` 的 `ok`。第 12 步的仅包名只在走得到第 12 步时出现。证书非空且第 11 步成立时，该包是云端正常，不进三截，仅包名规则不再显示。禁止把仅包名当成联网后仍出现的关注名单。演示用风险必须走第 2 步：包名、证书、`certAlgo` 都填对，并且 `certAlgo` 与 `BundleFinger` 在本机读到的算法一致。

高置信本地黑规则只认两种：

- 文件：`kind=file`，`sha256` 非空且与规则全等，规则 `level` 为 `risk`。已装应用的 `sha256` 不拿来对文件黑规则。
- 包：`bundleName`、`certSha256`、`certAlgo` 都非空，包名全等，`certAlgo` 与规则行相同，规范化后的证书全等，规则 `level` 为 `risk`。

仅包名、空证书、空哈希都不是高置信。JSON 里若把仅包名或空证书写成 `risk`，`RulePack` 加载时降为第 12 步，并打一条 hilog。不丢弃该行。证书非空、但 `certAlgo` 缺失或不是 `platform-fingerprint`、`sha256-of-cert-bytes` 的行：忽略，打一条 hilog，不降级成仅包名。`certAlgo` 是合法值、但与设备不一致的行不忽略，也不因此判风险。它只是第 8 步的材料，不在 `terminalBeforeCloud` 里返回。

同一包名有多行时，先分清数组，再放回主表。不能各判各的，也不能用这个选择跳过云端 `risk`、白哈希或信任：

1. `bundles` 里有一行构成高置信黑规则：按第 2 步。`terminalBeforeCloud` 返回 `risk`。证书或 `certAlgo` 没对上的 `bundles` 行不构成黑规则，也不构成冒名，不使用该行的 `reason`。
2. 否则 `officials` 里有一行登记相符：按第 6 步的材料。`terminalBeforeCloud` 返回 `null`。`decide` 里第 4 步的云端 `risk` 和第 5 步的白哈希仍先于第 6 步。
3. 否则 `officials` 里有一行包名全等、`certAlgo` 相同、证书不在该行允许列表里：按第 3 步。`terminalBeforeCloud` 返回冒名。这一步不看 `bundles`。
4. 否则按两类材料进入第 8 步，`terminalBeforeCloud` 返回 `null`。第 4、5、6 步已经结束就不再落到第 8 步。第 7 步在本条成立时不结束，已有信任也不能把它改成 `ok`。第一类：`officials` 的全等行全部 `certAlgo` 与设备不同；没有全等行时，只有 `Lookalike` 选中的那一条 `certAlgo` 与设备不同。距离内其它登记名不算。第二类：`bundles` 里包名全等、证书非空、`certAlgo` 与设备不同。没有 `bundleName` 的文件不调用 `Lookalike.select`，第一类只看包名全等。已装应用和读出了包名的安装包都调用 `select`；没有全等行时，第一类用的就是这个选中行。
5. 否则 `bundles` 里有一行包名全等、`certAlgo` 相同、两边证书都非空、规范化后的证书不同：按第 9 步。`terminalBeforeCloud` 返回 `null`，仍产生 `QueryKey`。第 4、5、6 步已经结束就不再落到第 9 步。第 7 步在本条成立时不结束，已有信任也不能把它改成 `ok`。这一行不是第 8 步的材料。

第 3 步只使用 `officials`，还要求设备证书非空。证书为空则不走第 3 步，也不走第 6 步。第 6 步还要求 `bundleName` 非空。文件的 `bundleName` 为空则不走第 6 步。`bundles` 里同名但证书不同的应用不写「签名与官方记录不符」。第 6 步已经相符的证书，不因为另一行黑名单写了别的证书而走进第 9 步。

登记证书行的 `certSha256` 数组为空则忽略该行，并打一条 hilog。该行不参加第 3、6、8、10 步。启发式规则少于 2 个权限则忽略。启发式的 `level` 写成 `risk` 时降为 `suspicious`，并打一条 hilog。降级的行不计入下面的 N 或 M。证书算法缺失或不是合法值而被忽略的行计入 N。空的登记证书数组、少于 2 个权限的启发式计入 M。N 大于 0 时，`exam.rules.version` 的 `detail` 包含「有 N 条规则暂不可用」。M 大于 0 时包含「有 M 条规则未启用」。两句都要时用顿号连成一句。这两种忽略都不改变该项状态。

包的信任要四项都相同：`kind=bundle`、`fingerprint`（规范化后的证书）、`id`（bundleName）、`versionCode`。`fingerprint` 必须是规范化后的非空串。空串不参与比较。包条目只覆盖被信任的那一个 `versionCode`。文件的信任只认 `kind=file-sha256` 和 `fingerprint`（sha256）。不比较 uri，不比较 `versionCode`。同一哈希换了 uri 仍然命中。uri 只留作显示和恢复时的默认路径。用户不能把 `certAlgo=none` 的包放进信任区；界面不提供这个动作。第 2 步、第 3 步、第 8 步和第 9 步已经结束的行不提供信任按钮。已经存在的信任条目也不能让这四步改判。第 7 步增加前提：第 8 步不成立，并且第 9 步不成立。这两步成立时第 7 步不结束，结果不得写成「已加入信任」。第 8 步或第 9 步仍成立时，下次扫描也不在第 7 步结束。当前这次扫描里，信任写入之后不改该行的 `level`，不改 summary 计数，也不把按钮写成「已信任」。撤权和从系统设置读回授权走 `rejudgeGranted`，那一次可以改等级；信任按钮仍不写成「已信任」，信任区条目留到下次扫描。按钮写「已添加信任，下次扫描生效」，这一行留在原来的可疑或未知里。下次扫描走到第 7 步之后，按钮才是「已信任」，该行不再进入三截。已能按第 7 步匹配的行，按钮直接是「已信任」，不再写一条。`Anomaly` 只看已授予权限，不看信任区。信任不减少 `anomalyApps`。

`cloud.state=reached` 且 `level` 不是 `ok`、`unknown`、`risk` 时，调用方应已把它收成 `offline`。`Decide` 若仍看见这种值，按 `offline` 处理，不按 `ok`。

信誉、体检和软件列表都走 `AppJudge`。查询键按 `cloudBatch` 分组，一组一次 `CloudBatch.query`。禁止对每个包串行发一次请求。禁止启发式把 `ok` 或 `risk` 改成别的等级。响应条目的下标对齐的是这一批请求里的 `QueryKey`，不是 `BundleCensus` 或文件列表的原始下标。第 1 到第 3 步没有产生 `QueryKey` 的对象不占位置。`ResponseCheck` 按请求下标核对回显之后，`AppJudge` 把这条 `CloudView` 交回产生该 `QueryKey` 的对象。禁止按已装应用数组的下标套用。

`Heuristic.matches` 是纯函数。一条规则里的权限必须全部出现才命中。只出现一项不算。命中多条时原因拼在一起，总长不超过 `reasonMax`。

- 已装应用：`grantsReady` 为 true 时，只在 `granted` 里找这些权限。原因前加「已允许：」。`grantsReady` 为 false 时，权限启发式不命中。禁止把空的 `granted` 当成「用户都没授权，所以正常」。`Anomaly.count` 不走这一条的 false 分支，它按第 8 节把快照里的 `granted` 当作 `grantsReady=true`。
- 安装包文件：`kind=file` 时只在 `declared` 里找。原因前加「安装包中声明：」。不看 `granted`。

权限页的异常计数另走 `Anomaly`，看的是 `ScanHit.granted`。`evidence=official` 的应用不计入异常。`source=trust` 仍计入。包名是 `com.jinyinhu.securitycenter` 的不计入，和 `sensitiveApps` 一样。只声明、未授予的不计。`Anomaly` 不使用 `InstallSource`。

`Lookalike.select` 和 `Lookalike.matches` 都是纯函数。比较的是 `bundleName`，不是文件名。已装应用，以及 `HapReader` 读出了非空 `bundleName` 的安装包，都调用 `select`。没有包名的普通文件不调用。

```ts
export interface LookalikePick {
  bundleName: string          // 没有选中行时为空串
  certAlgo: string            // 没有选中行时为空串
  certSha256: string[]        // 该行允许的证书。没有选中行时为空数组
}
```

`select` 的规则：

1. `bundleName` 与仍有效的 `officials` 全等时，不按距离挑选，返回的 `bundleName` 为空串。全等行另按第 3 步或第 6 步处理。全等行里只要有一条 `certAlgo` 与设备相同，就不因为另一条全等行算法不同走进第 8 步。全部全等行的 `certAlgo` 都与设备不同时，第 8 步用这些全等行，不用距离选中行。
2. 没有全等行时，计算与每条仍有效 `officials.bundleName` 的 Levenshtein 距离。较短的一边短于 `lookalikeMinLength` 时跳过该条。距离大于 `lookalikeDistance` 时跳过。距离相同取包名字典序较小的一条。只保留这一条，写入 `LookalikePick`。距离内的其它登记名不再参看。没有留下的条时，三个字段皆空。

已装应用和读出了包名的安装包，`decide` 在判断第 8 步之前调用 `select`。没有包名的文件不调用。第 8 步只读全等行或这次 `select` 的结果。禁止根据 `matches` 的 true 或 false 决定第 8 步。没有全等行、且 `LookalikePick.bundleName` 非空、其 `certAlgo` 与设备不同：第 8 步成立。此时不必调用 `matches`，也不得再走到第 11 步。`matches` 只在第 8 步不成立之后、走到第 10 步时调用。

`matches(pick, fp)` 只在第 10 步使用，并且只在第 8 步不成立时调用。`pick.bundleName` 为空则不命中。`certAlgo` 与设备不同则不命中。`certAlgo` 一致且规范化后的证书在 `certSha256` 里，不命中。`certAlgo` 一致且证书不在允许列表里，才命中，`evidence=lookalike`，原因里写 `pick.bundleName`。这不是风险，该行可以信任，信任只覆盖当前 `versionCode`。用另一条更远的登记名把选中行改成 `cert-uncompared`，是禁止的。

`BundleFinger` 取证书：

- 平台若返回 `signatureInfo.fingerprint`，用 `canonicalCert` 写入 `certSha256`，`certAlgo=platform-fingerprint`。禁止再对这段十六进制做一次 SHA-256。
- 只有证书字节时，对字节做 SHA-256，再经 `canonicalCert`，`certAlgo=sha256-of-cert-bytes`。
- 都没有：`certSha256` 为空，`certAlgo=none`。这种包只能停在 `unknown` 或启发式可疑，不能被仅包名规则打成 `risk`，也不能走第 3 步或第 6 步。第 11 步不得把它写成 `source=cloud` 的 `ok`。读出了包名但证书为空的安装包同样如此。没有包名的普通文件仍可按哈希走第 11 步。

`Hash.ets` 按 `hashChunk` 更新 SHA-256。`HashWorker` 用 TaskPool，并接收 `CancelFlag` 的 `SharedArrayBuffer`。Worker 起不来时，作业 `failed`，原因走 `io`，已完成条目保留。该次若是体检，同样调用 `settleStoppedExam`。禁止退回 UI 线程哈希。

`HapReader.read` 只用于扩展名是 `.hap` 的文件，并且调用方已经通过 `FileOpen`。全盘、自定义和安装包查找都走这一份，不另写一套：

1. 大于 `hapReadMax`：只算 `sha256` 和 `size`，其余字段空着。调用方在 `ScanHit` 的说明里写「安装包过大，仅校验了文件」。不打开压缩包。
2. 先读中央目录的条目名。条目名含 `..` 或以 `/` 开头：跳过该条，继续看后面的条目。不因此中止整个安装包，也不把该条当配置或签名。
3. 配置条目和签名块按条目名找，不计入 `hapEntriesMax`，也不因为其它条目已经解压了 200 条而放弃。排在第 201 条及以后的配置或签名仍要读取。`hapEntriesMax` 只限制配置和签名以外的条目的完整解压。单条解压超过 `hapEntryMax` 就放弃该条，继续按名字找配置或签名。配置和签名按名字找不到，或找到的那条超过 `hapEntryMax`：包名或证书留空，已经算完的哈希保留。调用方在说明里写「无法读取该安装包」。禁止因为条目序号超过 200 就把包名留空。
4. 能读出 `bundleName`、版本、`requestPermissions` 就填上。读不出就留空，不按文件名猜测包名。
5. 能从签名块取出证书，就按 `BundleFinger` 的规则填 `certSha256` 和 `certAlgo`。取不到就留空。禁止用文件哈希充当证书指纹。
6. 读配置失败不影响已经算完的哈希。不因此把整次信誉作业记成 `failed`。

`InstallSource` 由 `BundleCensus` 填写。当前 SDK 的 `BundleInfo` 声明里没有安装来源字段时，全部填 `unknown`，并打一条 hilog。禁止把 `unknown` 当成 `sideload`。

## 7. 规则与云

`rules/default_rules.json`：

```json
{
  "version": "2026.11.12",
  "bundles": [
    {
      "bundleName": "com.example.risk",
      "certAlgo": "platform-fingerprint",
      "certSha256": "替换为测试包的平台指纹",
      "level": "risk",
      "reason": "演示用风险包"
    }
  ],
  "officials": [
    {
      "bundleName": "com.example.official",
      "certAlgo": "platform-fingerprint",
      "certSha256": ["替换为发行版登记的证书指纹"],
      "reason": "签名与官方记录不符"
    }
  ],
  "files": [
    { "sha256": "", "level": "risk", "reason": "" }
  ],
  "heuristics": [
    {
      "id": "sms-and-contacts",
      "permissions": ["ohos.permission.RECEIVE_SMS", "ohos.permission.READ_CONTACTS"],
      "reason": "短信和通讯录"
    },
    {
      "id": "sms-and-call",
      "permissions": ["ohos.permission.SEND_MESSAGES", "ohos.permission.PLACE_CALL"],
      "reason": "短信和拨打电话"
    },
    {
      "id": "background-location-and-camera",
      "permissions": ["ohos.permission.LOCATION_IN_BACKGROUND", "ohos.permission.CAMERA"],
      "reason": "后台定位和相机"
    }
  ]
}
```

`bundles[].certSha256` 为空不能当高置信黑规则。`bundles[].certAlgo` 和 `officials[].certAlgo` 只能是 `platform-fingerprint` 或 `sha256-of-cert-bytes`。`officials[].certSha256` 为空数组则忽略该行，该行也不参加相似包名比较。`files[].sha256` 为空则忽略该行。`files[].level` 为 `ok` 且哈希非空，才是第 5 步的白哈希。为 `risk` 且哈希非空，才是文件黑规则。`heuristics` 只产生可疑。正式的黑名单和登记证书都要填满指纹和 `certAlgo`。演示包的 `certAlgo` 必须与 `BundleFinger` 在本机读到的算法一致：设备给出 `signatureInfo.fingerprint` 就填 `platform-fingerprint`，只有证书字节就填 `sha256-of-cert-bytes`。写错算法时该包进不了第 2 步。

`RECEIVE_SMS`、`SEND_MESSAGES` 的 `availableLevel` 是 `system_basic`，`PLACE_CALL` 是 `system_grant`。普通应用不会被授予这三项，已装的普通应用不会因前两条启发式变成可疑。安装包仍然按声明判断，声明里有这组权限就可以是可疑。`LOCATION_IN_BACKGROUND` 和 `CAMERA` 的等级是 `normal`。普通应用两项都已授予时，走 `background-location-and-camera`，结果仍只是可疑。只授予其中一项不命中。

规则版本串使用定宽日期 `YYYY.MM.DD`，必须匹配 `^\d{4}\.\d{2}\.\d{2}$`。不匹配的云端版本当作没有云版本，不比较，也不因此把 `exam.rules.version` 设为 `unknown`。不匹配的本地版本只显示原文，不参与「云上有新版本」。符合定宽时，才按 UTF-8 字节序比较。本轮只显示，不下载，不按版本替换文件。以后的服务只接受签名通过、且版本串符合定宽并大于上一份的包。坏包继续用服务侧的上一份。本轮不读 HAP 沙箱里另存的 JSON。

规则只从 `rawfile` 读入。本轮不下载规则，不解析外部 JSON 当作规则包。`RulePack` 不做云验签；云验签只在 `ResponseCheck`。读失败或 JSON 损坏：若内存里已有上一份，继续用上一份，体检建议项写「规则文件损坏，仍使用上一份」；若没有上一份，`center.rulesVersion=none`，体检状态项 `exam.rules.version` 为 `risk`。

云客户端 `ReputationClient` 实现 `CloudBatch`。请求体只有查询键：

```text
  ]
}
```

禁止在请求里放 `id`、uri、`version`、`label`、声明权限或文件正文。`JSON.stringify` 之后的正文不得包含用户授权 uri。


公钥是 `rules/reputation_pub.pem`，对应 `kid=primary`。文件不存在，或没有配置服务地址：不发请求，相关条目的 `CloudView.state=offline`，`level=none`，原因「未联网，云服务未配置」。

`ResponseCheck.accept` 是纯函数。下面任一条件成立，整批拒绝，每条都是 `state=offline`、`level=none`，原因「未联网，云端结果无效」：

- `alg` 与 `cloudAlg` 不一致
- `kid` 与 `cloudKid` 不一致
- `nonce` 与本次请求不一致
- 验签失败
- 条目数与请求不一致
- 任一字段含 `|` 或换行
- 回显的 `bundleName`、`versionCode`、`certSha256`、`sha256` 与请求对应项不一致

签名覆盖的字节是一段 UTF-8 文本：`nonce`，换行，`version`，换行，然后每个 item 一行：`bundleName|versionCode|certSha256|sha256|level|reason|evidence`。行序与响应 `items` 一致。这一行里的 `versionCode` 是十进制整数的最短写法：不用小数点，不加前导零，零就写 `0`。请求 JSON 里的 `versionCode` 是数字。回显比对和验签都先把数字收成这个写法再比。签名文本里写成 `01` 或 `1.0`，整批拒绝。

验签通过之后，某条 `level` 不是 `ok`、`unknown`、`risk`：只把该条收成 `offline`。其余条目仍可用。

不使用本机时钟判断响应是否过期。这块板的时钟会回到错误年份，不能当作防重放的依据。防重放只靠本次 `nonce`。旧的合法响应因为 `nonce` 对不上而被整批拒绝。轻车道和重车道同时查询时，两次请求各有自己的 `nonce`，禁止共用一个字段。

超时、非 200、JSON 不合格，与整批拒绝相同，都是 `offline`，作业仍是 `done`。这三种的行内原因是「未联网」。公钥缺失或没有服务地址的行内原因是「未联网，云服务未配置」。整批拒绝或单条 `level` 不合法而被收成 `offline` 的行内原因是「未联网，云端结果无效」。上文和验收里写的「云失败的那一句」就是这三句，全文固定，都含「未联网」。禁止再写「未配置云公钥」或「云响应未通过校验」而不带「未联网」。作业级 `CenterError.message` 仍用第 13 节的短句，不拿那张表代替行内原因。

```text
POST /reputation/hint
正文只有一个 QueryKey。仅当用户在该行点「提交检测」。
```

没有公钥、没有服务时，界面不出现「云查杀已开启」。

## 8. 体检

`ExamState.ets` 的 `stateOf(items): ExamState`：

1. 计入状态的项是 `countsTowardState === true` 的项。`advice` 不参与。`attention` 只出现在 `advice` 上，不参与。
2. 计入状态的项里有 `risk` → `risk`。
3. 否则若存在 `id === 'exam.malware.apps'` 且 `status === 'unsupported'` → `incomplete`。该项仍放在「暂不支持」，`countsTowardState` 仍是 false。
4. 否则计入状态的项里有 `unknown` → `incomplete`。
5. 否则一条计入状态的项都没有 → `incomplete`。
6. 否则全部是 `ok` → `clear`。
7. 以上都不满足 → `incomplete`，并打一条 hilog。计入状态的项只允许 `ok`、`risk`、`unknown`。`attention` 只放在不计入状态的建议项上。

姿态比较用同一条规则，防护页也用它。`pureMode` 的 `actual` 先规范成字符串：数字 `1`、布尔 `true` 和字符串 `1` 都变成 `1`，等于 `1` 才是 `ok`。`lockdown` 的 `actual` 去掉首尾空白后等于 `confidentiality` 才是 `ok`。读不到仍是 `unsupported`。其它值是 `risk`。

圆环文案只有四句，禁止数字，禁止「已安全」：

| 状态 | 文案 |
|---|---|
| `not-run` | 尚未体检 |
| `risk` | 有风险 |
| `incomplete` | 未完成 |
| `clear` | 暂无风险 |

`clear` 的圆环下方先写「本次只检查了已安装应用」。这句不把 `clear` 改成 `incomplete`。授权目录里的文件要到信誉页做全盘或自定义才会进入判定。若 `skipped > 0`，再写「另有 N 项暂无法检查」。有 advice 时再写「有 N 条建议」。`suspiciousApps > 0` 时再写「发现 N 个可疑应用」，N 用 `suspiciousApps`。可疑应用和权限异常算在建议里，不把圆环改成「有风险」。应用信誉项的 `detail` 含「未联网」且该项状态仍是 `ok` 时，圆环下方再写「部分应用未联网，结果来自本地」。应用信誉项的 `detail` 含「云端暂无结果」且该项状态仍是 `ok` 时，圆环下方再写「部分应用云端暂无结果」。这几句不把 `clear` 改回 `incomplete`。该项状态不是 `ok` 时，圆环已经不是「暂无风险」，只用该项详情里的「未联网」和「云端暂无结果」，圆环下方不再重复这两句。`detail` 含「部分应用暂无法确认」时，圆环下方写这一句，不把 `incomplete` 改回 `clear`。

`ExamRunner` 按下列顺序跑，进度文案依次是「正在检查系统安全」「正在扫描应用」「正在计算可清理空间」「正在检查应用权限」。一项失败只影响该项，不中断后面的项。不调用 `ProbeMap`，不调用 `probe/`。`group` 用于结果页分组，不参与 `stateOf`。

| id | group | kind | 做什么 | 计入状态的条件 |
|---|---|---|---|---|
| `exam.protect.pure-mode` | protect | state | `PosturePort.pureMode` | 读到了才计入。按上面的姿态规则，规范后等于 `1` 为 `ok`，否则 `risk`。读不到为 `unsupported`，不计入 |
| `exam.protect.lockdown` | protect | state | `PosturePort.lockdown` | 读到且为 `confidentiality` 才是 `ok`。读到别的值是 `risk`。读不到是 `unsupported`，不计入 |
| `exam.protect.el5` | protect | state | `PosturePort.el5` | 读到且服务在才是 `ok`。读到且不在是 `risk`。没有查询接口是 `unsupported`，不计入 |
| `exam.malware.apps` | threat | state | `AppJudge` 判定已装应用，快照写入 `ExamReport.apps`。范围等于信誉页的 `quick`。`grants()` 为 `ready` 时先读已授予权限 | 调用 `examAppsStatus`。包列表不可用则该项不计入状态。没有其它 `risk` 时，`stateOf` 仍得到 `incomplete`。其余见下一段 |
| `exam.malware.suspicious` | threat | advice | 同一份快照里 `level === 'suspicious'` 且 `action === 'none'` 的个数 | 个数大于 0 时 `status=attention`，否则 `ok`。都不计入圆环。`summary.suspiciousApps` 等于这个个数 |
| `exam.rules.version` | rules | advice | 本地规则版本；云版本只有验签通过才比较 | 本地规则缺失 → 改成 state，`risk`，计入。云失败或云上有新版本 → `unknown`，保持 advice，不计入 |
| `exam.permission.anomaly` | permission | advice | `Anomaly.count`：启发式里的权限组合必须都已授予，才算一个应用。`evidence=official` 的应用不计入。`source=trust` 仍计入。本应用不计入 | 授权状态不可用 → `unsupported`，不计入，详情写「无法读取授权状态」。人数大于 0 为 `attention`，否则 `ok`。都不计入圆环。`summary.anomalyApps` 等于这个人数 |

`ExamState.ets` 导出 `examAppsStatus`。`ExamRunner` 写 `exam.malware.apps` 时只能调用它，禁止在 Runner 里再写一套分支。

```ts
export function examAppsStatus(
  bundlesReady: boolean,
  appsComplete: boolean,
  riskApps: number,
  unknownApps: number,
  anyOffline: boolean
): AppsItemStatus
```

`bundlesReady` 为 false：`status=unsupported`，`countsTowardState=false`，`detail` 为「无法获取应用列表」。不看另外四个参数，也不要把 `appsComplete=false` 抬成 `unknown`。

`bundlesReady` 为 true 时，`countsTowardState=true`，状态按这个顺序：

1. `riskApps > 0` → `risk`。
2. 否则 `appsComplete` 为 false，或 `unknownApps > 0` → `unknown`。
3. 否则 → `ok`。`suspicious` 不进入这个函数，不把这项打成 `risk`。

`appsComplete` 为 false 时，`detail` 含「本次扫描未完成」。`anyOffline` 为 true 时，`detail` 含「未联网」。两句都要时用顿号连成一句。都不要时 `detail` 为空串。凡是调用 `examAppsStatus` 并把结果写回 `exam.malware.apps`，写回后若 `apps[]` 里仍有 `action===none`、`level===ok`、原因含「云端暂无结果」的行，`detail` 再含「云端暂无结果」。已含有则不重复。若仍有 `action===none` 且 `evidence=heuristic-cleared` 的行，`detail` 再含「部分应用暂无法确认」。已含有则不重复。状态和 `countsTowardState` 不因这两句改变。四句同时存在时用顿号连成一句，顺序是「本次扫描未完成」「未联网」「云端暂无结果」「部分应用暂无法确认」。

`anyOffline` 为真，当且仅当 `apps[]` 里存在 `action===none`、`level===ok`、`source` 不是 `cloud`、`cloud===offline` 的行。可疑、未知和风险行不把它写成 true。这些行自己的原因仍可保留「未联网」。体检写应用信誉项、`settleStoppedExam`、处置回写和 `rejudgeGranted` 都用这一句。禁止把任意 `cloud=offline` 的行算进去。

四个计数在截断和到点之前写好，只数 `action === 'none'` 的已判定应用：`riskApps`、`suspiciousApps`、`unknownApps`、`okApps`。判定循环里每追加一条这样的 `ScanHit`，同一笔 `Writer` 写入里把对应计数加 1。收尾时四个计数必须等于截断前、`action===none` 的已判定条数。不等则以截断前的判定结果改写计数，并打一条 hilog。禁止按截断后留下的 `apps[]` 把 `okApps` 或 `unknownApps` 改小。`settleStoppedExam` 同样禁止改小：只在 `summary` 里该等级的数小于 `apps[]` 中仍在的 `action===none` 行数时，把该等级抬到这个行数。截断后的数组可以短于计数。`appsComplete` 在下面任一情况为 false：应用循环因为文件数、字节或时间上限停住；或者截断时丢掉了 `unknown`。`risk` 和 `suspicious` 不因为 `listMax` 被丢掉。只丢掉 `ok` 时 `appsComplete` 仍为 true。安装包统计到上限不改变 `appsComplete`。包列表不可用时 `apps` 为空，`appsComplete=false`，状态仍是 `unsupported`。

断网本身不产生 `source=cloud` 的 `ok`。离线时走不到第 4 步和第 11 步。停在第 5、6、7 步的是 `ok`，`source` 不是 `cloud`，`cloud=offline`。停在第 10 步的是 `suspicious`，`cloud=offline`。停在第 8、9、12、13 步的是 `unknown`，`cloud=offline`。这些步得到的 `unknownApps > 0`，或 `appsComplete` 为 false 且 `riskApps` 为 0 时，应用信誉项为 `unknown`，圆环为「未完成」。`riskApps > 0` 时该项仍是 `risk`。包列表不可用时该项是 `unsupported`，没有其它 `risk` 时圆环是「未完成」，不是「暂无风险」。不得因为云失败而写成 `source=cloud` 的 `ok`。只有可疑、未知或风险行 `cloud=offline`、没有任何上面定义的本地 `ok` 时，`anyOffline` 为 false。应用信誉项详情不因此含「未联网」，圆环下方也不写「部分应用未联网，结果来自本地」。重新打开结果时不从 `apps[]` 重算这项，圆环读已经写好的 `CheckItem`。

`summary.cleanableBytes` 由 `CleanMath` 计算，并且清理页的合计用同一份函数。安装包名单只来自 `InstallerScan.listInstallers` 的 `hits`。缓存字节加上这份名单里 `residue` 和 `installer` 的字节：读不出包名因而不会列出的文件不算。`CorpseFinder` 必须调用同一份函数，禁止 `ExamRunner` 再按扩展名另扫一遍。每一条加进去的缓存或安装包都写入 `summary.parts`：缓存的 `id` 是 `bundleName`，安装包的 `id` 是 uri。`cleanableBytes` 写成 `parts` 的 `bytes` 之和。不等时以 `parts` 之和改写 `cleanableBytes`，并打一条 hilog。应用判定和安装包统计各用各的文件数、字节和时间。安装包是否统计完只看 `stoppedByLimit`。为 true 时不改 `appsComplete`，只在备注追加「部分安装包未统计」。为 false 时不追加这句。缓存端口不可用时只把本应用 `cacheDir` 写入 `parts`，备注加上「仅统计了本应用缓存」。没有文件授权时不写安装包 `parts`，备注加上「目录未授权，安装包未计入」。备注用顿号连成一句 `cleanableNote`。本应用缓存也失败，并且没有安装包授权时，`cleanableKnown=false`，`parts` 为空，`cleanableBytes=0`，`cleanableNote` 为空串，首页不显示这句。只要 `parts` 里有一条，`cleanableKnown=true`。缓存和安装包都测全、也没到上限时，`cleanableNote` 为空串。这一项不生成 `CheckItem`。体检写入 `ScanHit.granted`：`grants()` 为 `ready` 时写入该包当时已授予的权限名，否则为空数组。文件的 `granted` 为空数组。减法只减 `parts` 里已有的同一 `id` 和 `kind`。缓存见第 9.2 节，安装包只在第 9.1 节减一次。

`summary.sensitiveApps` 是至少持有一项已授予敏感权限的应用数，不含本应用。`grants()` 不是 `ready` 时 `sensitiveKnown=false`，`sensitiveApps=0`，首页不显示这句，也不写成「没有应用持有敏感权限」。`grants()` 为 `ready` 时 `sensitiveKnown=true`，人数为 0 也显示。这一项不生成 `CheckItem`。普查数字和 `exam.permission.anomaly` 是两件事。首页第三句只用 `sensitiveApps`，禁止填 `anomalyApps`。`anomalyApps` 只出现在体检结果的权限异常建议里。

`Anomaly.count(hits)` 只数已装应用：`fingerprint.kind` 为 `bundle`，`bundleName` 不是 `com.jinyinhu.securitycenter`，`action===none`，`verdict.evidence` 不是 `official`，并且 `Heuristic.matches` 命中。调用时把该条 `granted` 当作 `grantsReady=true` 的已授予列表，不再询问 `SystemGate.grants()`。`granted` 为空数组表示当时没有已授予权限，不命中。禁止因为体检当时的门闸或此刻的门闸是 `unsupported`，就把已经写入的快照判成不命中。`source=trust` 不排除。不使用 `InstallSource`。体检在截断前的快照上调用它。授权状态不可用发生在写入快照之前：这时不调用 `Anomaly.count`，体检该项为 `unsupported`。处理成功后不拿截断后的数组重算，只在被处理的那一条原来计入时把 `anomalyApps` 减 1。`source === 'sideload'` 且持有已授予敏感权限、且不是本应用时，另计一条建议 `exam.permission.sideload`，`status=attention`，不计入圆环。当前 SDK 没有安装来源字段、`source` 全是 `unknown` 时不生成这一项，详情不写「没有侧载应用」。本轮不要为这项预留通过态。

结果页按组渲染，组内再分成四截：`kind === 'state'` 且状态是 `risk` 或 `unknown` 的放进「待处理」；`kind === 'advice'` 且状态是 `attention` 或 `unknown` 的放进「建议」；状态是 `ok` 的放进「正常」；`unverified` 和 `unsupported` 放进「暂不支持」。

`ProbeMap.toCheck(probeId, result)` 仍是纯函数，供「系统防护自检」使用。它按 `probeId` 翻译，禁止把 P1 的三条套到 P2 或 P3。看 `result.level` 和 `result.evidences`，不看探针类上的缺省 `level`。没有结果对象时是 `unverified`。`countsTowardState` 一律为 false：自检页自己显示，不进 `ExamReport`。`detail` 保留探针原短语。不改现有探针的 `run`、verdict 和证据。

P1：

1. 证据没有 `cmd-transcript` 也没有 `sidecar-state`，或 `result.level` 不是 `L2`，或 `verdict` 不是 `hit` 也不是 `blocked` → `unverified`。没有侧车时现有 P1 常返回 `blocked` 和「暂未发现异常」，必须走这一支，不得译成通过。
2. 否则 `hit` → `risk`，`blocked` → `ok`。

P2：

1. 证据里有不是 `errno` 的 `kind` → `unverified`。
2. `verdict=blocked`，并且至少有一条证据 `kind` 为 `errno` → `ok`。现有探针挡住时 `result.level` 为 `L1`，这一级算通过，不要求 `L2`，不要求侧车。
3. `verdict=hit` → `risk`。
4. 其它 → `unverified`。

P3：

1. `verdict=passive` → `unverified`。现有基础版走这一支。
2. `verdict=blocked` 且 `result.level` 为 `L2` → `ok`。证据可以是 `source-ref`，不要求 `cmd-transcript` 或 `sidecar-state`。现有安全版走这一支。
3. `verdict=hit` → `risk`。
4. 其它 → `unverified`。

动作：

| 项 | ActionRef |
|---|---|
| 三项防护 | `{ route: 'protect', params: '' }` |
| 应用信誉 | `{ route: 'malware', params: 本次 exam 的 jobId }` |
| 可疑应用 | `{ route: 'malware', params: 本次 exam 的 jobId }` |
| 规则版本 | `{ route: 'protect', params: 'rules' }` |
| 权限异常 | `{ route: 'permission', params: 'anomaly:' + 本次 exam 的 jobId }` |

体检过程中不隔离、不卸载、不清缓存、不关闭权限、不改信任区。用户从结果里点进信誉、清理或权限之后，在那些页面上确认，才发生处理。

## 9. 功能模块

每个 Runner 是纯逻辑，不持有界面状态。页面从 `ResultStore.read` 填 `@State`。源数据是结果文件。路由 `params` 只决定滚动和筛选，不能当作可以卸载或隔离的凭据。

### 9.1 应用信誉 `MalwareRunner`

页面标题是「应用信誉」。文件一截的标题是「文件检查」。

- `quick`：已装应用。体检的应用快照用这一档。每条 `ScanHit.granted` 按第 8 节写入。
- `full`：已装应用，加上 `FileGrant` 里 `persisted === true` 且 `FileOpen` 现在仍能打开的 uri。已装应用的 `granted` 与 `quick` 相同。没有持久授权：只扫应用，`note` 含「目录未授权，未扫描」。授权打开失败：只扫应用，`note` 含「授权已失效」。失效的 grant 从清单删除。扩展名是 `.hap` 的先经 `HapReader`，再交给 `AppJudge`。其它文件也交给 `AppJudge`：哈希、文件规则，以及 `terminalBeforeCloud` 返回 `null` 时的云批次。没有声明权限时，权限启发式不命中。文件的 `granted` 为空数组。
- `custom`：只扫这一次选择器返回的、且通过 `FileOpen` 的 uri。扩展名是 `.hap` 的先经 `HapReader`，再交给 `AppJudge`。其它文件同样交给 `AppJudge`，规则与 `full` 里的文件相同。禁止只做本地文件规则就结束。

每个对象一条 `ScanHit`，写入 `ScanReport.hits`。`action` 默认 `none`。处理列表默认不勾选。`MalwareRunner` 只写结果，不隔离、不卸载。

打开文件之前先走 `FileOpen`。被 `FileOpen` 拒绝，或读到上限时，这个 uri 不进入哈希。

结果页分三截，顺序固定：风险、可疑、未知。`ok` 不进主列表。`ScanReport.complete` 为 true 时，摘要先写「另有 N 项无异常」，N 等于 `ok`。`complete` 为 false 时不写「另有 N 项无异常」，也不再统一写成「本次扫描未完成」。两种情况下，摘要再原样接上 `note`。从体检打开时，N 用 `summary.okApps`；`appsComplete` 为 false 时同样不写「其余 N 个」。任一 `action===none` 且 `level===ok` 的行，原因含「云端暂无结果」时，摘要再写「部分应用云端暂无结果」。这句不改变 `complete` 或 `appsComplete`，也不写入 `note`。风险行的来源要能区分黑名单、登记证书不符和云端风险，用 `verdict.evidence` 与 `verdict.source`。`evidence=official` 的正常结论不进主列表。可疑行的标题写「可疑」，不写「病毒」。`evidence=lookalike` 的原因里保留官方包名。`evidence=cert-uncompared` 和 `evidence=bundle-cert-mismatch` 都放在未知一截。`verdict.cloud === 'offline'` 的行在原因里保留「未联网」。

`params` 若是某次体检的 `jobId`，页面只用来读取那次 `ExamReport.apps` 和 `summary`，不重新入队，也不写入 `JobRequest`。用户点「开始」才跑新的信誉作业。这次入队 `focus` 恒为空串。`scope` 用页面上选的档。`uris` 只在 `custom` 时写入。宫格上的开始和体检后的开始，在同一档、同一组 `uris` 时是同一个请求。快速扫描进行中，再从体检点同一档开始，页面显示「正在扫描」，不打开另一份结果。权限页仍把路由 `params` 写入 `focus`。`anomaly:` 加体检 `jobId` 不和 `focus` 为空的全量权限作业合并。

`examWritebackTargets()` 返回至多三份已收口体检，按 `jobId` 去重：用户正在看的已收口 `ExamReport`；最近一次 `state===done` 的体检；第 14 节的 `settledHome()`。清缓存、隔离安装包和卸载都只改这三份里真正含有目标的那几份。没有该包、该文件或对应 `parts` 条目的那份不改。不新增 `JobRecord`。正在 `queued` 或 `running` 的体检不在这三份里，避免和正在写结果的 Runner 同时改 `apps[]`。缓存或安装包的减法若发现这份正在跑的结果里已经有同一条 `parts`，只减这一条，不改 `apps[]`，也不改作业状态。

用户点「立即处理」后走 `Disposition`。`Disposition` 不接受 `duplicate` 和 `large-file` 的结果。它只接受当前信誉结果、当前体检结果或当前清理结果里存在的包名或 uri：

- 文件能移动，且 `level` 不是 `ok`：`Quarantine.put`。成功后把该条 `quarantined` 改为 true，`action` 改为 `quarantine`。
- 应用不能移动：`InstallerPort.uninstall`。成功则 `action` 改为 `uninstall`。系统拒绝则保留该行，摘要写返回码。
- 信任只出现在等级为 `suspicious` 或 `unknown`、并且证书非空、`evidence` 不是 `impersonation`、`cert-uncompared` 或 `bundle-cert-mismatch`，并且 `source` 不是 `local-black` 的行上。文件行改为要求 `sha256` 非空。包写入规范化后的 `certSha256`、`bundleName` 和 `versionCode`。文件写入 `sha256`，uri 只作显示。已经能走到第 7 步的行，按钮写「已信任」，不再写入。这次新写入的行，按钮写「已添加信任，下次扫描生效」，`level` 和人数都不变。`evidence=cert-uncompared` 和 `evidence=bundle-cert-mismatch` 都不提供信任。
- 每行可以打开权限页，`params` 为该 `bundleName`。权限页按第 9.6 节查找，不因为没跑过权限作业就写成「没有该应用的记录」。
- 目标作业仍是 `queued` 或 `running` 时，`Disposition` 拒绝。不卸载、不隔离、不撤权、不清缓存、不写信任。页面显示「扫描尚未完成」。
- 目标作业已收口时：结果文件里必须已有这一行，且 `action===none`。信誉和体检只处理风险、可疑或未知行。清理只处理当前页已勾选的缓存或安装包。没有这样的行时仍拒绝，页面显示「扫描尚未完成」。成功后不把 `interrupted`、`failed`、`cancelled` 改成 `done`。
- 隔离或卸载成功后，先改用户正在看的那份已收口结果里的这一行：`action` 改为 `quarantine` 或 `uninstall`。这份若是 `ScanReport`，且该行原来的 `action` 是 `none`，按其 `level` 把 `risk`、`suspicious`、`unknown` 或 `ok` 减 1，不小于 0。`judged` 不减。`complete` 保持原值。不因为 `judged` 大于四个等级之和把 `complete` 写成 false。不在 `ScanReport` 上调用 `examAppsStatus` 或 `stateOf`。
- 然后再回写体检，目标是 `examWritebackTargets()`。正在看的那份若是已收口的 `ExamReport`，回写这一份。最近一次 `done` 和 `settledHome()` 若是另外的份，并且 `apps[]` 里有同一个包或文件，也回写。正在看的不是体检时，仍然回写最近一次 `done` 和 `settledHome()`，不因为当前页是信誉或清理就漏掉首页正在采用的那份中断体检。没有目标的那份不改。每一份都按下面的规则各写一次。失败不改任何体检。读改写都在 `Writer` 的队列里完成。隔离文件时，对每一份被回写的体检按第 9.2 节的减法处理，`id` 用 uri，`kind` 用 `installer`。`parts` 里没有这条就不减。有这条时同样先减 `bytes`、再把 `cleanableBytes` 改成 `parts` 之和。`cleanableNote` 不动。

回写一份已收口的 `ExamReport` 时：先按处理前的 `action`、`granted` 和 `verdict` 判断这条原来计入哪些计数，再改 `action`。`examAppsStatus` 的 `bundlesReady` 用这份里 `exam.malware.apps` 已经写下的 `countsTowardState`，不读此刻的 `SystemGate`。`appsComplete` 保持原值。`anyOffline` 用第 8 节的定义：只看这份里 `action===none`、`level===ok`、`source` 不是 `cloud`、`cloud===offline` 的行。目标不在这份 `apps[]` 里时，不改应用计数。

- 该行原来的 `action` 是 `none` 时，按其 `level` 把 `riskApps`、`suspiciousApps`、`unknownApps` 或 `okApps` 减 1，不得减成负数。然后用减完的 `riskApps`、`unknownApps` 调用 `examAppsStatus`，并按第 8 节补「云端暂无结果」和「部分应用暂无法确认」。
- 该行原来计入 `Anomaly` 时，`anomalyApps` 减 1。用减完的人数更新 `exam.permission.anomaly`：大于 0 为 `attention`，否则 `ok`。授权项原来是 `unsupported` 时不改它。
- 该行是已装应用、不是本应用、原来至少有一项已授予的敏感权限时，`sensitiveApps` 减 1，不小于 0。`sensitiveKnown` 保持原值。
- 这次处理是卸载已装应用时，对每一份被回写的体检去掉 `parts` 里 `id` 等于该 `bundleName`、`kind` 为 `cache` 的那一条，`cleanableBytes` 改成剩余 `parts` 之和。`cleanableNote` 不动。没有这条就不改字节。安装包文件还在磁盘上，不因为卸载而去掉 `kind` 为 `installer` 的条目。
- 可疑建议项用减完的 `suspiciousApps`：大于 0 为 `attention`，否则 `ok`。
- 按更新后的 `items` 重算 `advice`。最后 `state = stateOf(items)`。
- 从软件页卸载成功时，从当次软件结果去掉该行，并按 `examWritebackTargets()` 回写。`settledHome()` 可以是 `interrupted`、`failed` 或 `cancelled`。不新增 `JobRecord`。只追加一条审计。禁止写一条 `state=running` 的作业。

### 9.2 清理 `CleanRunner`

主作业 `kind=clean` 产出 `CleanReport`：`caches` 和 `hits`。重复文件和大文件仍是各自的 `FileToolReport`，从清理页进入，不进这次合计，也不进体检状态。`params=duplicate` 入队 `kind=duplicate`，`params=large` 入队 `kind=large-file`。禁止把这两个入口入成 `kind=clean`。没有触到第 4 节的三个上限时 `complete=true`。触到时 `complete=false`，`note` 含「已达本次扫描上限」。`complete` 为 false 时，不把空列表写成没有缓存或没有安装包。重开页面显示 `note`，不另造一句。

应用缓存：

- `CacheStats` 可用时，对已装应用逐个取缓存字节。字节为 0 的不列出。本应用也在列表里。
- 不可用时，只列本应用 `cacheDir` 的合计一条，`bundleName` 为本应用。`note` 含「无法读取其他应用缓存」。不返回空列表冒充没有垃圾。
- 读入页面时缓存行一律默认勾选。写回文件时 `selected` 仍为 false。转屏或从记录重开，仍按这一句重新默认勾选，不把文件里的 `false` 当成用户取消了全部勾选。勾选只存在当前页的 `@State`。处理按钮看当前页勾选，不看文件。
- 确认后由 `Disposition` 调用 `CacheClear`，或在只有本应用这一条时直接删除 `cacheDir` 里的文件。不调用 `Quarantine.put`。不调用任何会删除应用数据的接口。失败的行留下，并写原因。`Disposition` 只清除结果文件里存在的 `bundleName`。成功后对 `examWritebackTargets()` 里每一份调用 `subtractPart(bundleName, 'cache', 实际清掉的字节)`。`parts` 里没有这个 `id` 和 `kind` 时，这一份的 `cleanableBytes` 不变。有这条时，`bytes` 减去实际清掉的字节，不小于 0；减到 0 就去掉这条。然后 `cleanableBytes` 改成 `parts` 之和。`cleanableNote` 不动。首页正在采用的中断、失败或取消体检因此也会减字节，不只改最近一次 `done`。

安装包使用 `CorpseFinder` 的结果，放进 `hits`。读入页面时默认不勾选。页面提供「全选」和「取消全选」，只改当前这一类的勾选。

顶部显示已勾选缓存之和，加上已勾选安装包之和。确认文案带上这个字节数和条数，并写明缓存会直接清除、安装包会进隔离区。

不提供扫描全盘并删除。系统前缀由 `FileOpen` 和 `Exclude` 拒绝。

### 9.3 安装包 `CorpseFinder`

不按目录名或文件名等于包名来判断。系统卸载会清掉应用私有目录，这种文件名匹配会碰到用户自己的文件。`CorpseFinder` 只调用 `InstallerScan.listInstallers`，再把 `hits` 写成 `FileHit`。`stoppedByLimit` 按第 9.3 节写入 `note`。禁止再实现一遍打开、扩展名和 `HapReader`。

`engine/InstallerScan.ets` 导出：

```ts
export interface InstallerScanHit {
  uri: string
  name: string
  size: number
  bundleName: string
  sha256: string              // HapReader 已经算出的文件哈希。没算成则为空串
  reason: string              // 只有下面两句
  clazz: 'residue' | 'installer'
}

export interface InstallerScanResult {
  hits: InstallerScanHit[]
  stoppedByLimit: boolean     // 只表示触到 maxFiles、maxBytes 或 deadlineMs。取消和没有授权都是 false
}

export function listInstallers(
  files: FileSource,
  open: FileOpen,
  installed: string[],
  stopped: () => boolean,
  maxFiles: number,
  maxBytes: number,
  deadlineMs: number
): InstallerScanResult
```

`stopped` 由调用方接到 `CancelFlag`。函数不 import `task/`。额度用调用方这一项的剩余值。同一组授权目录、已装集合和额度，两次调用的 `hits` 的 uri 集合必须相等，`stoppedByLimit` 也必须相等。触到文件数、字节或时间上限时立刻返回，`stoppedByLimit=true`。取消只在额度未到时返回，`stoppedByLimit=false`。禁止把取消写成「部分安装包未统计」。

规则：

1. 没有授权时 `hits` 为空，`stoppedByLimit` 为 false。清理页这一类只有一句「请先选择目录」，写入 `CleanReport.note`，不写「没有安装包」。体检不写安装包 `parts`。
2. `FileOpen` 拒绝的 uri 直接丢掉，不打开。
3. 扩展名不是 `.hap` 的丢掉。
4. `HapReader` 读出 `bundleName`。读不出就跳过，不列入结果。
5. `bundleName` 不在已装集合中 → `clazz='residue'`，`reason` 为「该应用未安装」。
6. `bundleName` 已安装 → `clazz='installer'`，`reason` 为「已安装应用的安装包」。
7. `sha256` 抄 `HapReader` 已经算出的文件哈希。没算成就留空串。禁止用包名或证书指纹填这个字段。
8. 两类都默认不勾选。`CorpseFinder` 把 `hits` 里的 `uri`、`name`、`size`、`sha256`、`reason`、`clazz` 抄进 `FileHit`，`selected` 为 false，`groupId` 为空串。`stoppedByLimit` 为 true 时，`CleanReport.complete=false`，`note` 含「已达本次扫描上限」。确认后才 `Quarantine.put`。`sha256` 为空串时由 `put` 自己计算。成功后的体检回写只走第 9.1 节那一次 `subtractPart(uri, 'installer', size)`，目标是 `examWritebackTargets()`。这里不再减第二遍。没有对应 `parts` 条目时不减。

`ExamRunner` 用同一份 `hits` 写入 `summary.parts`。`id` 是 uri，`kind` 是 `installer`，`bytes` 是 `size`。`stoppedByLimit` 为 true 时，`cleanableNote` 追加「部分安装包未统计」。为 false 时不追加这句，即使 `hits` 为空。

### 9.4 重复文件 `DuplicateFinder`

参数类型是 `FileToolContext`。没有缓存端口，也不调用 `Quarantine`。

1. 只看当次选择器或仍有效的持久授权，并且 `FileOpen` 允许打开。
2. 按 `size` 分组。组内只有 1 个的丢掉，不算哈希。
3. 受 `heavyMaxFiles`、`heavyMaxBytes`、`heavyBudgetMs` 约束。
4. 组内再算 SHA-256。哈希相同的组成一个 `DuplicateGroup`，每个 `FileHit.groupId` 指向它。
5. 全部 `selected=false`。结果里不编码「保留第一条」。
6. 清理页主列表不包含这一项。入口在清理页下方，文案是「重复文件」。没有授权时入口仍在，点进去先选择目录。页面只有「开始」，没有「立即处理」。不调用 `Quarantine.put`，也不删除。页上写「仅查看，不删除」。

### 9.5 大文件 `LargeFileFinder`

参数类型是 `FileToolContext`。没有缓存端口，也不调用 `Quarantine`。

授权范围内、且 `FileOpen` 允许打开、`size >= 100MB` 的文件，`reason` 取最高一档：`size >= 1GB` 写 `1GB+`，否则 `size >= 500MB` 写 `500MB+`，否则写 `100MB+`。不默认勾选。不进体检状态，也不进清理主列表的合计。入口在清理页下方，文案是「大文件」。页面只有「开始」，没有「立即处理」。不进隔离区，也不删除。页上写「仅查看，不删除」。`quarantineQuota` 装不下这一档，用户视频也不做加密复制。同样受三个上限约束。

### 9.6 权限 `PermissionRunner`

`BundleCensus` 不可用时，页面只有一句「无法获取应用列表」，不画空表，不写「未发现风险」。

可用时产出 `PermissionFact[]`。声明来自包信息。`grant`、`fixed` 只有 `SystemGate.grants()` 为 `ready` 时才填；否则 `grant` 全部为 `unknown`，`fixed` 为 false。列名在未知时写「状态未知」。禁止把声明显示成已授权。

`fixed=true` 当且仅当 `getPermissionFlags` 含下列位之一：`PERMISSION_SYSTEM_FIXED`、`PERMISSION_FIXED_FOR_SECURITY_POLICY`、`PERMISSION_FIXED_BY_ADMIN_POLICY`。其它标志不表示系统固定。`PERMISSION_PRE_AUTHORIZED_CANCELABLE` 本身不表示不能关闭。

`SensitiveCatalog` 是纯函数，分组固定为：

| 组 | 权限 |
|---|---|
| 位置 | `LOCATION`、`APPROXIMATELY_LOCATION`、`LOCATION_IN_BACKGROUND`、`MEDIA_LOCATION` |
| 相机 | `CAMERA` |
| 麦克风 | `MICROPHONE` |
| 通讯录 | `READ_CONTACTS`、`WRITE_CONTACTS` |
| 日历 | `READ_CALENDAR`、`WRITE_CALENDAR` |
| 短信 | `RECEIVE_SMS`、`SEND_MESSAGES` |
| 电话 | `PLACE_CALL`、`ANSWER_CALL`、`READ_CALL_LOG` |
| 媒体 | `READ_MEDIA`、`READ_IMAGEVIDEO`、`WRITE_IMAGEVIDEO`、`READ_AUDIO`、`WRITE_AUDIO`、`READ_DOCUMENT` |
| 其它 | 上面没有的声明 |

权限名都带前缀 `ohos.permission.`。`sensitive` 为真的只有前八组。`READ_MEDIA` 虽已标记废弃，已装应用仍可能持有，计入媒体组，也计入 `sensitiveApps`。目录里的权限若实际不是 `user_grant`，仍可展示，但不提供关闭。

页面：

1. 顶部是八个敏感组，每组一个已授予人数。这是普查。权限页入队时 `scope=quick`，`focus` 等于当前路由 `params`。`params` 为空则 `focus` 为空串。不同 `focus` 不算同一个请求。`params === 'sensitive'` 时停在顶部。`params` 为组名时只展开该组。`params` 以 `anomaly:` 开头时，冒号后面是体检 `jobId`。只读那一份已收口的 `ExamReport`，用其中 `apps[]` 的 `granted` 和 `verdict` 按 `Anomaly.count` 展开。`evidence=official` 的不展开。`source=trust` 仍按 `granted` 展开。本应用不展开。这些行的名单仍是那次体检的快照。页顶写「以下为该次体检的授权记录」。开关看当前授权，不看快照里的 `granted`。开关按第 3 条：当场读到的 `accessTokenId` 非 0，当前 `grant===granted`、`fixed===false`，并且 `revoke()` 为 `ready`。禁止用体检或权限结果 JSON 里的旧 `tokenId` 调用 `revoke`。成功后按本节 `rejudgeGranted` 重判这份体检里的该包；这份若不是最近一次 `done`，最近一次 `done` 的体检里同一个包也重判。最近一次 `done` 的信誉结果含这个包时同样重判。`settledHome()` 若是另一份且含这个包，也重判。当前已不是 `granted` 时没有开关，该行写「已关闭」。`fixed===true` 时没有开关，该行写「受系统限制」。`revoke()` 不是 `ready` 时没有开关，该行写「无法关闭此权限」。读不到 `tokenId` 或读到 0 时没有开关，该行写「无法读取授权」。这份体检不存在，或作业仍是 `queued` 或 `running` 时，显示「没有该次体检记录」。`params` 为包名时，名单先用当前权限结果里该包的行；没有则用最近一次 `done` 的体检或信誉结果里该包的 `granted` 作为权限名，页顶写「权限来自上次扫描，开关为当前状态」。无论名单来自哪一份，都对这一个包当场读取 `accessTokenId` 和当前授权，开关按第 3 条。不因为还没有权限作业就隐藏「关闭权限」。三份名单都没有、并且当场列不出这个包，才显示「没有该应用的记录」。
2. `params` 以 `anomaly:` 开头时，名单只来自那份体检的 `apps[]`，不改用 `PermissionFact[]`。名单不改。关闭按钮是否出现，按上一条读当前授权。其余页面按权限聚合、按应用展开，数据都来自同一份 `PermissionFact[]`。应用行显示它持有的敏感权限个数。
3. `grant === 'granted'` 且 `fixed === false` 且 `tokenId` 非 0 且 `SystemGate.revoke()` 为 `ready` 时，该行按钮是「关闭权限」。`tokenId` 必须是这一次 `bundleManager.getBundleInfo` 读到的 `ApplicationInfo.accessTokenId`。为 0、字段不存在或这次读取失败时没有开关，该行写「无法读取授权」，不要发撤权。确认文案包含应用名、权限中文名，以及「关闭后，该应用无法再次申请此权限，需到系统设置中重新开启」。成功后把该条 `grant` 写成 `denied`，`action` 记到审计，并写回权限结果。然后对该包调用 `rejudgeGranted`：先从目标行的 `granted` 去掉这项权限，再按下面的规则重判。失败则保留 `granted`，摘要带返回码，体检和信誉结果都不动。
4. `fixed === true` 时文案是「受系统限制，无法关闭」，没有开关。`revoke()` 不是 `ready` 时，所有行都没有开关，页顶写「无法关闭此权限」。不把用户带去一个不存在的设置页。
5. 不提供授予。用户要打开一项权限时，仍去系统设置，本应用不调用授予接口。
6. 本轮没有权限复申请的常驻监听。按钮和结果文案用「关闭权限」，不用「已防护」或「已拦截」。
7. `SystemGate.usedStats()` 为 `ready` 时，页底增加「最近使用」：`AccessFacts.recentUses()`，最近 `useLookbackMs`、最多 `useListMax` 条，新的在前。数组为空时写「最近 7 天没有使用记录」。不是 `ready` 时这一段不画，也不写「最近没有使用记录」。

从系统设置返回本应用、导致 `SystemGate` 缓存失效时，若权限页正在显示，丢弃内存里的开关状态，入队一次 `permission` 作业，`focus` 等于当前 `params`。相同请求已在排队或运行则沿用该 `jobId`。新结果写完之前显示「正在刷新授权」。`params` 以 `anomaly:` 开头时，这段时间不把体检里的旧 `granted` 画成当前授权。新的权限结果写完后，按 `rejudgeGranted` 回写。不把整份 `apps[]` 换成权限作业。

`rejudgeGranted` 用于撤权成功，以及从系统设置读回授权。不调用 `decide` 全表，不发起云查询，不改 `action`，不改 `appsComplete`，不删信任区条目。第 7 步还没走到的行，不把按钮改成「已信任」。先按旧的 `granted` 记下这一行原来是否计入 `Anomaly`、原来是否持有已授予敏感权限，再把 `granted` 改成新的已授予权限名，然后重判。

只处理 `fingerprint.kind=bundle` 且 `action===none` 的行。文件行不改 `verdict`。`level=risk`，或 `source` 为 `trust`、`local-black`，或 `evidence` 为 `official`、`impersonation`、`cert-uncompared`、`bundle-cert-mismatch`、`empty-fingerprint` 的行，只改 `granted`。其余行用新的 `granted` 重跑 `Heuristic.matches`，并调用 `Lookalike.select`。规则用当前已加载的 `RulePack`。第 8 步成立时不必调用 `matches`。

  - `verdict.cloud=reached`，并且原因含「云端查询正常」，并且证书非空、`certAlgo` 不是 `none`：按第 11 步，`level=ok`，`source=cloud`，原因「云端查询正常」。`okApps` 或 `ok` 加 1。不增加 `unknown`。

  - 否则：`level=unknown`，`source=local-rule`，`evidence=heuristic-cleared`，原因「风险权限已关闭」。`cloud` 保持原值。`source` 不是 `cloud`。禁止写成 `ok`。证书为空或 `certAlgo=none` 时同样停在这里。`cloud=offline` 时原因末尾追加云失败的那一句。`cloud=reached` 且旧原因里已有「云端暂无结果」时，这句留在末尾。`unknownApps` 或 `unknown` 加 1。`evidence=heuristic-cleared` 只出现在 `rejudgeGranted`。下次完整扫描仍走第 1 到第 13 步。没有新的命中时停在第 13 步，等级仍是 `unknown`，`evidence` 不再是 `heuristic-cleared`。因此这一次就把圆环收成「未完成」，不先写成「暂无风险」。应用信誉项 `detail` 按第 8 节含「部分应用暂无法确认」，圆环下方也写这句。
- 原来不是可疑，现在两项也都不命中：不改 `verdict`，不改四个等级计数。

计数不得小于 0。`judged` 不减。`ScanReport.complete` 保持原值。不因为 `judged` 大于四个等级之和把 `complete` 写成 false。不改 `riskApps`，也不改 `ScanReport.risk`。

同一份结果里有多行要改时，先改完每一行的 `granted`、`verdict` 和四个计数，再做一次收尾。`anyOffline` 用第 8 节的定义：只看这份里 `action===none`、`level===ok`、`source` 不是 `cloud`、`cloud===offline` 的行。回写 `ExamReport` 时，调用 `examAppsStatus(该项的 countsTowardState, 原来的 appsComplete, riskApps, unknownApps, anyOffline)`。第二个参数用原来的 `appsComplete`，不因为这次重判改成 false。然后按第 8 节补「云端暂无结果」和「部分应用暂无法确认」。不得把该项改成 `unsupported`。可疑建议项用改完的 `suspiciousApps`：大于 0 为 `attention`，否则 `ok`。没有该项时不补。每一行按重判前是否计入 `Anomaly` 分别加减，再汇总到 `anomalyApps`。`evidence=official` 的仍不计入。包名是 `com.jinyinhu.securitycenter` 时，`anomalyApps` 和 `sensitiveApps` 不动。授权项原来是 `unsupported` 时不改它，其它情况按人数更新为 `attention` 或 `ok`。每一行按重判前是否持有已授予敏感权限分别加减，再汇总到 `sensitiveApps`。然后重算 `advice`，`state = stateOf(items)`。`ScanReport` 只改该行和四个等级计数，不调用 `examAppsStatus`。

`AccessFacts.facts` 先读 `ApplicationInfo.accessTokenId`，写入 `PermissionFact.tokenId`。调用是 `bundleManager.getBundleInfo`，flag 取本 SDK 里带应用信息的那一个；字段名以 d.ts 里的 `accessTokenId` 为准。不要调用 ETS 没有导出的 `getHapTokenID`。读不到、字段不存在或值为 0：该包 `tokenId=0`，不调用 `getPermissionsStatus`、`getPermissionFlags`、`revokeUserGrantedPermission`，`grant` 写 `unknown`，`fixed` 为 false。非 0 时，这三个接口都用这个 `tokenId`。`GrantLookup` 由同一个 `AccessPort` 实现。`ready()` 为 false 时不读授权。`AccessRevoke.revoke` 调用 `revokeUserGrantedPermission(tokenId, permission, PERMISSION_USER_FIXED)`。第三个参数必须是 `PERMISSION_USER_FIXED`（`1 << 1`）。禁止传 `0` 或 `PERMISSION_USER_SET`。`tokenId` 为 0 时不调用。授权状态或撤权被拒绝，就分别把 `grants()` 或 `revoke()` 记为 `unsupported`。

### 9.7 软件 `AppRunner`

列出 `BundleRow`。排序：`risk`、`suspicious`、`unknown`、`ok`，同级按包名。判定走同一份 `AppJudge`。`grantsReady` 为 false 时不产生权限可疑。

只读，不写系统参数。实现只走 `PosturePort`。禁止打开 `/sys/kernel/security/lockdown`，禁止让 HAP 执行 shell。三个方法各自调用，禁止因为 `SystemGate.posture()` 不是 `ready` 就把三项一起写成 `unsupported`。

## 10. 系统门面与以后的服务

`SystemGate.probe()` 在启动时跑一次，之后每次 `enqueue` 若缓存超过 `gateCacheMs` 再跑。用户刚授权文件后立刻失效缓存。从系统设置返回本应用时也失效缓存。禁止把一次 `unsupported` 缓存到进程结束。

```ts
export interface SystemGate {
  bundles(): Gate             // getAllBundleInfo 是否成功
  grants(): Gate              // GET_SENSITIVE_PERMISSIONS，授权状态
  revoke(): Gate              // REVOKE_SENSITIVE_PERMISSIONS，关闭授权
  usedStats(): Gate           // PERMISSION_USED_STATS，最近使用
  cacheStats(): Gate          // 各应用缓存大小的 SDK 方法是否存在且调用成功
  clearCache(): Gate          // 只清缓存的 SDK 方法是否存在且调用成功
  uninstall(): Gate           // installer.uninstall 探测是否被拒
  persistFileGrant(): Gate    // 当前 SDK 有没有授权持久化方法
  userPickedFiles(): Gate     // 选择器，恒为 ready
  ownCache(): Gate            // 恒为 ready
  posture(): Gate             // 以后的态势服务。本轮三项不看这个 Gate
  huks(): Gate                // 隔离区密钥能否生成
}
```

`BundleCensus.list()` 在 `bundles()` 不是 `ready` 时抛 `CenterError('unsupported', gate.reason)`。Runner 收成一条检查或一条空状态说明，不返回空数组冒充「没有应用」。

`CacheStats.stats` 优先调当前 SDK 里 `storageStatistics.getBundleStats`，只用其中的缓存字节。`CacheClear.clear` 优先调 `bundleManager.cleanBundleCacheFiles`。写代码前先对照本工程 SDK 的 `d.ts`。方法不存在、名称不同，或调用被拒绝时，对应 Gate 为 `unsupported`。禁止改走未声明的私有接口。统计不可用时清理页退回本应用缓存；清除不可用时，已列出的其它应用行保留，处理时该行失败并写返回码。

`module.json5` 已有 `GET_BUNDLE_INFO`、`GET_BUNDLE_INFO_PRIVILEGED`、`INSTALL_BUNDLE`。其余权限写入 `module.json5` 和镜像的 profile ACL。运行时被拒，对应的 Gate 就是 `unsupported`。

本 SDK 列出全部应用走 `getAllBundleInfo` / `getAllApplicationInfo`，要求 `GET_INSTALLED_BUNDLE_LIST`，并且调用方是系统应用。`GET_BUNDLE_INFO_PRIVILEGED` 不能代替列表权限，它用来按包名取 `BundleInfo`（含签名）。`bundles()` 以列表调用成功为准。列出时必须带 `GET_BUNDLE_INFO_WITH_SIGNATURE_INFO`，或列出后再用已有的 `GET_BUNDLE_INFO_PRIVILEGED` 补证书。某一包没有 `fingerprint` 时该包 `certAlgo=none`，不把整个 `bundles()` 打成 `unsupported`。

`uninstall()` 以 `installer.uninstall` 的探测调用为准。本 SDK 卸载校验在 `INSTALL_BUNDLE` 或 `UNINSTALL_BUNDLE` 任一授予时通过。现有工程已有 `INSTALL_BUNDLE`。禁止只因表里没有 `UNINSTALL_BUNDLE` 就把 Gate 写成 `unsupported`。

| 权限 | 等级 | 授予方式 | 用来做 |
|---|---|---|---|
| `GET_INSTALLED_BUNDLE_LIST` | system_basic | `user_grant`，且 `availableType` 为 `SYSTEM` | 列出其它应用。本 SDK 的 `getAllBundleInfo` 检查这一项 |
| `GET_BUNDLE_INFO_PRIVILEGED` | system_basic | `system_grant`，工程里已有 | 按包名取签名和证书。不能代替上一行 |
| `GET_SENSITIVE_PERMISSIONS` | system_basic | `system_grant` | 读授权状态和 flag |
| `PERMISSION_USED_STATS` | system_basic | `system_grant` | 最近使用 |
| `STORAGE_MANAGER` | system_basic | `system_grant` | 各应用缓存大小 |
| `REMOVE_CACHE_FILES` | system_basic | `system_grant` | 只清缓存 |
| `REVOKE_SENSITIVE_PERMISSIONS` | system_core | `system_grant` | 关闭一项授权 |
| `INSTALL_BUNDLE` | system_core | `system_grant`，工程里已有 | 本 SDK 卸载校验接受这一项 |

`REVOKE_SENSITIVE_PERMISSIONS` 的 `availableLevel` 是 `system_core`，`provisionEnable` 为 true。当前签名 profile 的 apl 是 `system_basic`。APL 低于权限等级时，该项写进 profile 的 `allowed-acls` 就会在安装时授予，`revoke()` 可以变成 `ready`。不把整个应用改成 `system_core`。没写进 ACL 时，`revoke()` 保持 `unsupported`。权限页只在 `revoke()` 为 `ready` 时画「关闭权限」。不按这张表预画开关。

`GET_INSTALLED_BUNDLE_LIST` 只放进 ACL 仍可能是未授予。镜像预授权清单里要有这一项。未授予时，`bundles()` 为 `unsupported`。体检过程中不调用 `requestPermissionsFromUser`。用户稍后可以在软件页点「读取应用列表」，拒绝之后本次进程不再弹，Gate 保持 `unsupported`。

`GET_SENSITIVE_PERMISSIONS` 和 `REVOKE_SENSITIVE_PERMISSIONS` 的权限定义带 `deviceTypes`。列表里有 `general` 时，表示全设备，手机和平板都要把这两项写进 `module.json5`。列表里既没有 `general`、也没有当前设备类型时，才不要写进 `module.json5`，对应 Gate 保持 `unsupported`。禁止把设备类型 `phone` 和 `general` 做字符串不相等就省略这两项。

`FileGrant`：

- 选择器返回的 uri 只保证当前作业能读。
- SDK 若有授权持久化方法，且用户在该次结果上点「记住此目录」，才写入 grant，`persisted=true`。
- 方法不存在：`persistFileGrant() = unsupported`。`full` 不读旧目录。每次全盘都要重新选目录。这是「暂无法记住目录」，不是扫描失败。摘要写「目录未授权，未扫描」。
- 持久化之后 `FileOpen` 失败：删除该条，摘要写「授权已失效」。

`FileOpen` 在任何读取、哈希、解包、隔离之前调用：

1. 能解析出路径时，先取 realpath。原路径和 realpath 都要检查。解析不出路径则跳到第 6 条。
2. 原路径或 realpath 被 `isHardExcluded`：返回 `rejected-system-path`，不打开。授权覆盖不了。
3. 计算授权根：当次选择器目录或仍有效 `FileGrant` 目录的 realpath。目标 realpath 必须等于授权根，或在授权根加 `/` 的下面。否则返回 `rejected-system-path`，不打开。
4. 授权根不是私有数据路径，而目标是：返回 `rejected-system-path`，不打开。这挡住从别的目录链进 `/data/app` 或 `/data/service`。
5. 授权根是私有数据路径时，目标必须仍在授权根之下。设 `rootSeg` 为 `privateBundleSegment(授权根)`，`targetSeg` 为 `privateBundleSegment(目标)`。`rootSeg` 非空时，`targetSeg` 必须为空或等于 `rootSeg`。`rootSeg` 为空时，`targetSeg` 必须为空。否则返回 `rejected-system-path`，不打开。用户目录因此可以读，别的应用的 `base/<包名>` 不能读。
6. 解析不出路径的 uri，必须来自当次选择器或一条仍有效的 `FileGrant`，否则返回 `rejected-system-path`。打开后系统若给出真实路径，立刻按第 2 到第 5 条再查。不通过就关闭描述符，不哈希、不复制。
7. 通过之后才把描述符交给哈希、`HapReader` 或隔离复制。

`PosturePort` 本轮由进程内适配器实现，不等待 `jyh_security_center`。三个方法各自探测，互不影响。禁止因为服务不在、或 `SystemGate.posture()` 不是 `ready`，就把三项一起写成 `unsupported`。`ProtectRunner` 和 `ExamRunner` 直接调这三个方法。本轮不在 HAP 里做常驻监听，仍禁止打开 `/sys/kernel/security/lockdown`，禁止执行 shell。

对照本工程 SDK 的只读系统参数接口。方法不存在或调用被拒，该方法自己返回 `unsupported`。

- `pureMode`：读 `persist.jyh.pure_mode`。读到则按第 8 节比较。
- `lockdown`：先读 `const.jyh.lockdown`，没有再读 `persist.jyh.lockdown`。读到则按第 8 节比较。安全版要在防护行看出差异，镜像必须把当前模式写进这两个键之一，值是 `confidentiality`、`integrity` 或 `none`。这不是态势进程。两个键都没有时该项是 `unsupported`，不得改写纯净模式和 el5 的结果。
- `el5`：对照本工程 SDK 是否能查询文件加密服务是否在。没有查询接口才是 `unsupported`。

本轮不实现服务进程。进程内的 `Decide`、`AppJudge`、`CloudBatch`、`Writer` 和各端口就是服务以后要接的那一份，禁止在服务里再写一套判定。

```text
服务名 jyh_security_center
以后的职责：
  持有规则、信任区、审计日志、隔离区密钥
  开机启动
  安装完成时只对这一个 bundleName 调用 AppJudge，向审计日志追加一条
  向 HAP 提供只读快照：姿态、包普查、权限事实、缓存字节、待处理事件
  用户在 HAP 确认之后，才执行卸载、清缓存、撤权、隔离
禁止：
  执行任意命令、结束进程、读其它应用私有文件内容、自己弹窗
本轮 HAP：
  端口由进程内适配器实现
  不订阅安装广播，不申请常驻
  用户动作和作业完成写入同一份审计格式
```

## 11. 防误删与隔离区

`feature/clean/Exclude.ets` 导出：

```ts
export function isHardExcluded(path: string): boolean
export function isPrivateDataPath(path: string): boolean
export function privateBundleSegment(path: string): string
```

比较前不要求路径以 `/` 结尾。命中是指路径等于前缀，或前缀后面紧跟 `/`。

`isHardExcluded` 的前缀是 `/system`、`/vendor`、`/chip_prod`、`/proc`、`/sys`、`/dev`。

`isPrivateDataPath` 的前缀是 `/data/app`、`/data/service`。

`privateBundleSegment` 在路径里找 `/base/<段>` 或 `/database/<段>`。段不含 `/`，结尾可以是字符串结束或 `/`。找到则返回该段，否则返回空串。有多处时取最靠前的一处。

不再导出把 `/data/app` 整段拒绝的 `isExcluded`。安装包查找不进入其它应用私有目录，这条由 `FileOpen` 的包名段检查完成。应用缓存不进入隔离区，只走 `CacheClear`。大文件和重复文件不进入隔离区。

`Quarantine.put` 不自己比前缀，再次调用 `FileOpen`。被拒绝则返回 `rejected-system-path`，源文件保持不动。

隔离区密钥：

- HUKS 别名 `jinyinhu.center.quarantine`。
- AES-GCM，密钥长度 256。密钥只留在 HUKS，禁止导出。
- 明文只写临时文件。加密完成或失败后，在 `finally` 里删除临时文件。
- `huks()` 不是 `ready` 时，`put` 返回 `unsupported`。隔离目录不留下明文，清单不增加条目。

布局：

```text
filesDir/center/quarantine/manifest.json
filesDir/center/quarantine/blobs/<id>     id 为 32 位随机十六进制，无扩展名，内容是密文
```

`put` 的顺序：

1. 配额不足 → `quota`，不写文件。配额按明文 `size` 累计。
2. 复制到临时文件。复制失败 → `io`，不写清单。
3. 对临时文件做 SHA-256。调用方给出的 `sha256` 非空、且与副本不一致 → 删临时文件，返回 `io`，源文件不动。调用方给出的是空串：采用这次算出的哈希写入清单。空串表示还没算，不是已经给出的指纹。
4. 加密到 `blobs/<id>`，清单记录 `iv` 和 `tag`。加密失败 → 删临时文件和半成品密文，不写清单。
5. 删除临时明文。
6. 清单的读取、把条目写成 `committed=false`、再用临时文件替换 `manifest.json`，整段都在 `Writer` 里做完。禁止在队列外读出清单、改完再提交替换。
7. 删除源。删除失败：条目保留，`committed=false`，界面写「副本已保存，原文件仍在」。启动时不自动再删源。
8. 删除成功后把该条改成 `committed=true`。这次读改替换同样整段在 `Writer` 里完成。

恢复：先解密，再算明文哈希。与清单不一致则拒绝，条目保留，目标位置不写入这份明文。写回前，目标路径必须通过 `FileOpen`。原路径仍在授权内就写回 `from`，否则让用户另选目录并改清单里的 `from`。另选的目录同样先过 `FileOpen`。不通过则拒绝，清单不动，目标位置一个字节都不写。写回成功后才从清单去掉。写回失败则清单不动，并删掉这次没写完的目标文件。

删除隔离项要第二次确认，文案包含文件名和大小。没有「清空全部」。

备份：`backup_config.json` 必须排除隔离区。若只写 `allowToBackupRestore: true`，系统会把沙箱一并备份。若本 SDK 的配置支持 `excludes`，至少写入隔离目录：

```json
{
  "allowToBackupRestore": true,
  "excludes": [
    "/data/storage/el2/base/files/center/quarantine"
  ]
}
```

路径写法以本 SDK 的 `backup_config` 说明为准。若该 SDK 没有 `excludes`，把 `allowToBackupRestore` 设为 `false`。禁止在无法排除隔离区时保持「整包允许备份」。`EntryBackupAbility` 不读取、不上传 `filesDir/center/quarantine`。

## 12. 记录

大块数据进文件。preferences 名仍是 `jinyinhu`，新键带前缀 `center.`，只放小值。不占用探针已有文件。

结果文件是界面缓存，不是审计证据。能改 HAP 沙箱的人可以改这些 JSON。审计以追加日志为准。

| 位置 | 内容 |
|---|---|
| `filesDir/center/jobs/index.json` | `JobRecord[]`，最多 `jobMax` 条，保住的体检可以暂时更多。只由 `Writer` 替换。超出时从 `seq` 最小的已结束记录开始丢，并删除该条结果文件。跳过 `queued`、`running`、`settledHome()` 和最近一次 `done` 的体检。跳过之后没有可丢的，允许暂时超过 `jobMax`，不得丢掉这两份体检 |
| `filesDir/center/jobs/<jobId>.json` | 该次结果。体检是 `ExamReport`，信誉是 `ScanReport`，清理主作业是 `CleanReport`，重复文件和大文件是 `FileToolReport`，权限是 `{ facts, uses }`，软件是 `BundleRow[]`，防护是 `ProtectFact[]` |
| `filesDir/center/quarantine/manifest.json` | `QuarantineEntry[]` |
| `filesDir/center/trust.json` | `TrustEntry[]` |
| `filesDir/center/audit.log` | `AuditLine` 的 JSON 行，只追加 |
| preferences `center.rulesVersion` | 当前本地规则版本 |
| preferences `center.grants` | `FileGrant[]`。只在持久化可用时写入 |

解析失败时不把坏文件删掉。`index.json` 解析失败：改名为 `index.json.bad-<时间>`，另起空索引，写 hilog，启动不崩溃。结果文件解析失败：保留原文件，页面写「无法读取该结果」，不显示成一次空的通过。审计日志最后一行不完整时忽略这一行，前面的行保留。

超过 `listMax` 的数组截到上限。计数在截断前完成。信誉写入 `ScanReport` 的 `judged`、`risk`、`suspicious`、`unknown`、`ok`。体检写入 `summary` 里的四个应用计数。体检没有 `judged`。扫描收尾、尚未处置也尚未 `rejudgeGranted` 时，`judged` 必须等于四个等级计数之和。不等则把 `ScanReport.complete` 写成 false，打一条 hilog，不改等级计数去凑等式。不因此改 `appsComplete`。处置和 `rejudgeGranted` 会减少四个等级计数、不减少 `judged`。这两处之后不再用这个等式改 `complete`。

保留顺序：全部 `risk`，再全部 `suspicious`，再 `unknown`，最后 `ok`。`risk` 和 `suspicious` 全部留下，即使两者之和超过 `listMax`。不允许出现计数里有、列表里没有的风险或可疑。`unknown` 和 `ok` 才受 `listMax` 限制；放不下的 `unknown` 使 `complete=false`，`note` 含「结果较多，仅显示部分」，体检则 `appsComplete=false`，`JobRecord.summary` 写「结果较多，仅显示部分」。状态仍用截断前的计数调用 `examAppsStatus`，不按留下的数组重算。只丢掉 `ok` 时，`complete` 可以为 true，「其余 N 个」用 `ok` 计数，不从数组里数 `ok` 行。

到点、到文件数或到字节时同样 `complete=false`，`note` 含「已达本次扫描上限」。截断丢掉 `unknown` 时 `note` 含「结果较多，仅显示部分」。两句都要时按结果说明的顺序用顿号连接。权限截断时先保留已授予的敏感权限。`FileHit.selected` 和 `CacheRow.selected` 写回文件时一律为 false。勾选只留在当前页面，不作为删除意图落盘。重新打开某次体检时，圆环读那份 `ExamReport.state` 和 `items`，不从 `apps[]` 重算。重新打开信誉、清理或文件工具时，没扫完的原因只读 `note`。没有正在跑的体检时，首页的圆环、三句数字、附加句和第五行按第 14 节的 `homeExam()` 读取，不从 `apps[]` 重算。正在跑的体检按第 14 节，不沿用上一份。没有可显示的体检时，首页仍是「尚未体检」。

现有 `Findings` 继续存探针证据。体检不写探针结论。两套记录不要合成一个「病毒」列表。

结果文件在第一条结果出现时就经 `Writer` 创建。`JobRecord.resultFile` 指向它。页面离开后再进 `JobResultView`，从该文件读。`JobResultView` 禁止用 `JobRecord.state===done` 显示「已完成」。体检读 `ExamReport.state` 和 `appsComplete`；信誉、清理和文件工具读报告里的 `complete`。作业是 `interrupted`、`failed` 或 `cancelled` 时，先显示作业状态那一句，再叠加结果里已经写下的风险。

作业完成、隔离、恢复、卸载、清缓存、撤权、信任各追加一条 `AuditLine`。`prepare` 不截断、不重写审计日志。

## 13. 错误

`CenterError`：`code` 为 `unsupported`、`cancelled`、`interrupted`、`rejected-system-path`、`io`、`cloud`、`unsigned-cloud`、`parse`、`quota`。`message` 给界面，`raw` 给记录。

| code | 用户看到的句子 | 作业 |
|---|---|---|
| `unsupported` | 当前系统不支持此功能 | 保持 `done`，条目单独标出 |
| `cancelled` | 已停止 | `cancelled` |
| `interrupted` | 扫描已中断 | `interrupted`。不阻塞下一次入队 |
| `rejected-system-path` | 系统目录已跳过 | 该条拒绝，作业继续 |
| `cloud` | 云查询失败，已使用本地结果 | `done`，条目 `cloud=offline`，等级按第 6 节 |
| `unsigned-cloud` | 云端结果无效 | `done`，条目 `cloud=offline`，`level` 不取响应里的值 |
| `io` | 文件处理失败 | 该条失败；哈希 Worker 起不来则整次 `failed` |
| `parse` | 规则文件损坏，仍使用上一份 | 启动不崩溃。坏索引被改名保留 |
| `quota` | 隔离区已满 | 该条拒绝 |

`unsigned-cloud` 和 `cloud` 都不得产生 `Verdict.level=ok` 且 `source=cloud`。第 5、6、7 步在 `cloud=offline` 时可以是 `level=ok`，此时 `source` 不是 `cloud`。这两行的行内原因用第 7 节的三句，不用上表的短句填进 `Verdict` 的原因。

## 14. 页面

`pages/Index.ets` 的打开方式是 `pushPathByName(route, params)`。`params` 是字符串；没有则为空串。禁止把路由名本身当作 `params`。`routeMap` 同时接收路由名和这个字符串。`HomeView` 的 `onOpen` 传入这两个值。宫格不带定位时，`params` 为空串。

`pages/Index.ets` 的 `routeMap` 增加：

| 路由 | 页面 | 入口 |
|---|---|---|
| `home` | 现有 HomeView | 启动 |
| `exam` | ExamView | 首页主按钮 |
| `malware` | MalwareView，标题「应用信誉」 | 宫格 |
| `clean` | CleanView | 宫格。`params` 为 `cache`、`installer`、`duplicate`、`large`。`residue` 与 `installer` 同义。`cache` 和 `installer` 入队 `kind=clean`。`duplicate` 入队 `kind=duplicate`。`large` 入队 `kind=large-file`。禁止把后两个入成 `kind=clean` |
| `permission` | PermissionView | 宫格 |
| `apps` | AppsView | 宫格 |
| `protect` | ProtectView | 宫格。`params=rules` 时定位到规则块 |
| `quarantine` | QuarantineView | 设置或信誉结果 |
| `job` | JobResultView | `params` 为 `jobId` |
| `P1` `P2` `P3` | 现有 ScanView | 路由不改。结论用 `ProbeMap` |
| `ledger` `report` `archive` `device` `about` | 现有页面 | 保持不动 |

`homeExam()` 决定首页采用哪一份体检：

1. 有 `kind=exam` 且作业为 `queued` 或 `running`：不采用任何已结束的体检。
2. 在 `done`、`failed`、`cancelled`、`interrupted` 里，取 `seq` 最大、且结果文件能解析成 `ExamReport` 的一份，记为 latest。禁止比较 `finishedAt`。`seq` 相同则取索引数组里靠后的一条。
3. latest 的作业不是 `done`，且 `ExamReport.state` 为 `risk`：采用 latest。圆环下写「本次体检未完成」。
4. 否则若存在 `done`：采用 `seq` 最大的那份 `done`。若 latest 不是这份，圆环下写「上次体检未完成」。
5. 没有 `done` 时，有 latest 就采用 latest，并写「本次体检未完成」。两份都没有，就是尚未体检。

`settledHome()` 使用上面的第 2 到第 5 步，忽略正在 `queued` 或 `running` 的体检。清缓存、隔离安装包和卸载回写它。体检正在跑时，`homeExam()` 不显示数字，`settledHome()` 仍指向跑完或取消后会露出来的那份。两者不要合成一个函数。开发板时钟回到错误年份时，后入队的风险体检 `seq` 更大，仍盖过先入队的「暂无风险」。

三个数字和第五行都从采用的这份读。第五行只读这份里的纯净模式、lockdown、el5。没有这份时第五行是「尚未检测」。之后单独跑完的防护作业只显示在防护页，不改首页。禁止圆环用一次体检、第五行用另一次防护。

首页：

1. 状态句和「开始体检」。未跑过是「尚未体检」。有 `kind=exam` 且 `state` 为 `queued` 或 `running` 时，状态句只用这条作业的 `message`。圆环不读上一份的四句，也不显示上一份的三句数字。这段时间不出现「暂无风险」「有风险」「未完成」。其它重作业进行时，仍显示 `homeExam()` 的圆环，进度句另外显示。
2. 没有正在跑的体检时，圆环使用 `homeExam()` 的 `ExamState` 四句，下方再用第 8 节的附加句，以及 `homeExam()` 第 3、4、5 步要求的「体检未完成」。
3. 圆环之外三句数字，都来自 `homeExam()` 的 `summary`：风险应用个数；`cleanableKnown` 时的可清理字节，备注非空就接上 `cleanableNote`；`sensitiveKnown` 时的敏感权限人数，人数取 `sensitiveApps`，禁止填 `anomalyApps`。对应标志为 false 时那一句不出现，不显示 0。没有 `homeExam()` 时三句都不出现。体检正在跑时这三句也不出现。这三句不参与圆环。
4. 四格：应用信誉、清理、权限、软件。第五行是防护，三个数都来自 `homeExam()` 里的对应 `CheckItem`。没有 `homeExam()` 时显示「尚未检测」，不显示全 0。探针个数不进这一行。
5. 现有「系统防护自检」磁贴。
6. 现有风险记录、报告、导入导出、设备信息、说明。

信誉页按风险、可疑、未知分截。清理页主列表是缓存和安装包，下方两个入口是重复文件和大文件。权限页顶部是敏感权限组。

应用信誉页和清理页底部两个主按钮：「开始」和「立即处理」。没有勾选时处理按钮不可用。重复文件页和大文件页只有「开始」，页上写「仅查看，不删除」。`enqueue` 返回空串时，页面显示「正在扫描」，并写明正在跑的是快速、全盘还是自定义，不新建结果页。从首页中断的有风险体检点进信誉页后，「立即处理」按第 9.1 节处理这份已收口结果里已经写下的行。体检页、防护页没有处理按钮。权限页用行内「关闭权限」。软件页用行内卸载。体检结果里的条目点进去，处理发生在信誉、清理或权限页。

18. 体检结束后，首页风险应用个数与 `summary.riskApps` 一致。`cleanableKnown` 或 `sensitiveKnown` 为 false 时，对应那一句不出现。敏感权限人数大于 0 本身不产生体检风险项。
19. 云响应验签失败、`kid` 不对或 `nonce` 不是本次请求时，整批 `cloud=offline`，没有任何一条变成云端正常。请求正文不含文件 uri。体检进行中打开软件页并发查询时，两边不得因为共用 `nonce` 一起变成未联网。
20. 杀掉进程后再打开：上次 `running` 的作业变为 `interrupted`，同一功能可以再次开始。坏的 `index.json` 被改名保留，应用仍能打开。被打断或失败的体检若收口后是「有风险」，首页圆环改为这份，并写「本次体检未完成」，不再显示上一份「暂无风险」。后入队的这份即使 `finishedAt` 早于上一份 `done`，仍然改读这份，因为比较的是 `seq`。索引超过 `jobMax` 时，首页正在采用的体检和最近一次 `done` 的体检仍在索引里。收口后不是有风险时，首页可以留着上一份 `done`，但必须写「上次体检未完成」。从记录打开这次 `interrupted`：已经有风险应用时总状态仍是「有风险」；`apps[]` 里已有风险而 `summary.riskApps` 仍是 0 时，总状态仍是「有风险」，并且 `riskApps` 被抬到这些行的条数，应用信誉项是 `risk`；还没有应用信誉项时是「未完成」。这几种都不是「暂无风险」。取消一份只写了姿态 `ok`、还没写应用项的体检，打开记录也不是「暂无风险」。扫描抛错记成 `failed` 的半成品，从记录打开也不是「暂无风险」。应用循环已经写完、`appsComplete` 为 true 时，在统计缓存或安装包阶段取消，或进程退出后再从记录打开：`appsComplete` 仍为 true，应用信誉项详情不含「本次扫描未完成」。没有风险和未知时，圆环不是「未完成」。应用循环没写完时 `appsComplete` 仍为 false。`suspiciousApps` 大于 0 而 `exam.malware.suspicious` 还没写时，收口后有这一条。
21. `Disposition` 收到一个不在当前结果文件里的包名或 uri 时，不卸载、不隔离、不撤权。`duplicate` 或 `large-file` 的结果也不能拿来隔离或删除。目标作业仍是 `queued` 或 `running` 时，不处理。已收口的中断体检若 `apps[]` 里已有风险行，从首页点进去可以处理这些行；处理成功后作业状态仍是 `interrupted`。
22. 卸掉体检结果里唯一的风险应用后，首页 `riskApps` 变为 0。该应用原来计入异常人数时，`anomalyApps` 同时减 1。这次 `appsComplete` 为 true、且没有未知时，圆环按剩余项重算。`appsComplete` 为 false 时，圆环不得变成「暂无风险」。处理之后列应用的权限掉了，这一份已经收口的应用信誉项不得改成 `unsupported`。在软件页卸掉 `homeExam()` 正在采用的那份里的同一个包，首页 `riskApps` 同样减少，并且不产生新的 `running` 作业。那份可以是 `interrupted`。该包在 `parts` 里有 `kind` 为 `cache` 的一条时，这条被去掉，可清理字节减去它。`kind` 为 `installer` 的条目还在，因为安装包文件还在。首页采用的这份若不是最近一次 `done`，清掉它 `parts` 里的一条缓存，或隔离它 `parts` 里的一条安装包，首页字节同样减少；最近一次 `done` 若是另一份且含同一条，那份也减。从较旧的一份 `done` 体检里卸载同一个包时，那份和最近一次 `done` 的计数都减少。
23. 信誉的快速扫描进行中再请求全盘，页面显示「正在扫描」，并写明正在跑的是快速，不产生第二份结果。正在跑的那次仍是快速。从体检 `jobId` 打开信誉页后点开始，`focus` 为空，和宫格上同一档的开始是同一个请求。快速扫描进行中再从体检点同一档，页面同样显示「正在扫描」。
24. 登记相符的应用在断网时可以是本地 `ok`，`source` 不是 `cloud`。详情含「未联网」。全部计入状态的项都是 `ok` 时，圆环是「暂无风险」，下方写「部分应用未联网，结果来自本地」。只有可疑行 `cloud=offline`、没有任何本地 `ok` 断网时，应用信誉项详情不含「未联网」，圆环下方不写这句。云端已经到达且 `level=unknown` 时，这条登记相符的原因里有「云端暂无结果」，等级仍是 `ok`。应用信誉项详情也含「云端暂无结果」。圆环是「暂无风险」时，下方写「部分应用云端暂无结果」。
25. 已装应用的 `sha256` 为空、没有本地黑名单、白哈希、信任或登记相符，并且断网：不是 `empty-fingerprint`。该行原因含「未联网」。应用信誉项为 `unknown`。该项 `detail` 不因这一行含「未联网」。
26. `bundles` 里同包名、同 `certAlgo`、证书不同，且没有 `officials` 行：信誉结果不是冒名，这次仍会发起云查询。云端返回验签通过的 `ok` 时，等级仍是 `unknown`，`evidence=bundle-cert-mismatch`，`source` 不是 `cloud`。云端返回验签通过的 `risk` 时，来源才是 `cloud`。登记相符的证书不因为另一条黑名单写了别的证书而变成这一条。
27. 全盘扫描里的 `.hap` 能读出包名。非安装包文件在云端哈希为验签通过的 `risk` 时，出现在风险一截，来源 `cloud`。
28. 配置条目排在第 201 条时，`HapReader` 仍读出包名。已经完整解压了 200 条其它条目，也不把这个包名留空。条目名含 `..` 时只跳过该条。
29. 文件信任之后，同一哈希用新的 uri 再扫，按钮是「已信任」，信任区不增加第二条。
30. 大小为 1GB 的文件，原因是 `1GB+`。云批次前面有一个已在第 2 步结束、没有 `QueryKey` 的包时，后面的云端 `risk` 仍落在发出该 `QueryKey` 的包上。
31. 已有一份 `done` 且圆环为「暂无风险」的体检时，再点开始体检：进行中首页不显示「暂无风险」，也不显示上一份的三个数字。这次变成 `done` 之后才改读新结果。
32. 体检仅统计了本应用缓存时，清掉别的应用缓存，首页 `cleanableBytes` 不变。隔离一个不在 `parts` 里的安装包，首页字节也不变。`stoppedByLimit` 为 false 时，体检备注不含「部分安装包未统计」。
33. 对一条可疑应用点信任后，这一行仍在可疑里，按钮是「已添加信任，下次扫描生效」，`anomalyApps` 不变。下次扫描走到第 7 步后，按钮才是「已信任」。这次扫描若仍满足第 8 步或第 9 步，结果仍是这两步，按钮不是「已信任」。权限页 `focus` 为 `anomaly:` 加体检 `jobId` 时，不和 `focus` 为空的全量权限作业并成同一个 `jobId`。从系统设置返回并读完新的授权后，这份体检的异常名单改用新的 `granted`。若可疑只来自已经关掉的权限组合，并且没有仅包名规则、也没有「云端查询正常」，该行进入未知，`evidence=heuristic-cleared`，`unknownApps` 加 1，不是 `ok`。相似包名仍在时留在可疑。从体检点进信誉页时，`params` 是那次 `jobId`，不是路由名 `malware`。

## 18. 明确不做

- 不链 ClamAV，不做特征码虚拟机，不做学习模型。启发式只看权限组合，相似包名只看编辑距离。两者的结果只叫可疑。
- 不扫描其它应用私有目录。不清应用数据，只清缓存。
- 不在管家里授予权限。关闭授权只走 `revokeUserGrantedPermission`，并且只带 `PERMISSION_USER_FIXED`。
- 不结束其它进程，不拦截短信和来电。
- 不在本轮 HAP 里订阅安装广播或申请常驻。安装时只扫一个包的契约写在第 10 节，等 `jyh_security_center` 进镜像后再接。本轮不把判定写进 HAP 页面，避免到时再写第二份。
- 不用体检分数。`unsupported` 和 `unverified` 不算「正常」。可疑、权限普查人数、可清理字节都不把圆环改成「有风险」。`unknown` 仍让圆环成为「未完成」。列不出已装应用、并且没有其它 `risk` 时，圆环也是「未完成」。没扫完时，除非已经有 `risk`，否则应用信誉项是 `unknown`，不得是 `clear`。
- 不用云端 `ok` 把同名黑名单证书不符或证书算法不一致改成正常。这两种也不写成可疑。证书为空或 `certAlgo=none` 的包也不写成 `source=cloud` 的正常。信任不减少权限异常人数。可清理字节不减 `parts` 里没有的条目。风险和可疑不因 `listMax` 从列表消失。处置和 `rejudgeGranted` 不因为 `judged` 未减把 `complete` 改成没扫完。中断、取消和失败按 `apps[]` 里已有的风险收口，不把总状态收成「暂无风险」。应用循环已经写完时不把 `appsComplete` 改成 false。只有可疑、未知或风险行断网时，不把「未联网」写进应用信誉项详情。
- 不把探针结果叫作病毒，不改现有探针的 verdict，不把探针放进体检。不把 P1 的 `ProbeMap` 三条套到 P2 或 P3。
- 不因态势服务不在把三项姿态一起标 `unsupported`。不打开 `/sys/kernel/security/lockdown`。不把 `JobRecord.state===done` 显示成已经扫完。不把 `anomalyApps` 填进首页敏感人数。不把仅包名规则当成联网后仍显示的关注名单。不因某一个包没有证书就把整个 `bundles()` 打成 `unsupported`。`ExamRunner` 不 import `CorpseFinder`。
- 不因为包名相同就判风险。不用未通过 `ResponseCheck` 的云响应判 `ok`。不用信任区挡住高置信黑名单、冒名、云端风险、证书算法不一致或同名黑名单证书不符。不用云端 `ok` 把可疑、证书算法不一致或同名黑名单证书不符改成正常。证书算法对不上时不判冒名，也不判可疑。选中行的证书算法与设备不同时先停在第 8 步，不掉进第 11 步。距离内没被选中的登记名不构成第 8 步。已有信任也不能把第 8 步和第 9 步写成「已加入信任」。登记相符不跳过云查询。云端明确没有结论时，登记相符和信任的原因里写上「云端暂无结果」。这句同时出现在应用信誉项详情里；该项为 `ok` 且圆环是「暂无风险」时，圆环下方也写。撤权或从系统设置读回授权后，启发式不再命中的行不再留在可疑里。选中行算法不同则进入第 8 步未知。有「云端查询正常」且证书非空、`certAlgo` 不是 `none` 时写成云端 `ok`。仅包名规则命中时进入未知。都没有时进入未知，`evidence=heuristic-cleared`，`unknown` 增加，不写成 `ok`。相似包名仍在时留在可疑。下次完整扫描没有新的命中时，等级仍是未知。圆环因此变成「未完成」时，下方写「部分应用暂无法确认」，不先写成「暂无风险」。首页按 `seq` 挑选体检，不按 `finishedAt`。索引满额时不丢掉 `settledHome()` 和最近一次 `done` 的体检。读出包名的安装包与已装应用使用同一个 `Lookalike.select`。
- 不提供隔离区「清空全部」。体检过程不自动卸载、不自动隔离、不自动清缓存、不自动关闭权限。大文件和重复文件不进隔离区，本轮也不删除。
- 不把 `filesDir` 里的 JSON 当作规则包。
- 不把文件 uri、路径、应用标签或声明权限上传到云。
- 不把隔离区放进备份，不在隔离目录保存明文样本。
- 界面不写「云查杀已开启」「已防护」「人工智能引擎已防护」。没有公钥或没有服务时，只写本地规则的结论。
